# デモ詳細LP 指示書（ケア記録DX型）

基準ページ: `/lp/kaigo-care-dx`（実体 `public/lp/kaigo-care-dx.html`）  
用途: 体験ギャラリーのデモ詳細ページを、このLPと同じ構成・同じ見た目の型で作るときの指示書。  
対象外: サイト全体のトップ、業種LP（`IndustryLpPage`）、プロトタイプ本体の操作画面。

この文書はルールである。新しい詳細ページを作るときも、既存の詳細をこの型へ寄せるときも、ここから外れる場合は理由を残す。

---

## 1. 何を移し、何をデモごとに変えるか

ケア記録DXの「介護の文章」を他業種へ貼らない。移すのは、読み進める順番、各ブロックの仕事、見た目の部品である。

| 固定（全デモ共通） | デモごとに書き換える |
|---|---|
| セクションの順番と、各節の役割 | 業種名、利用者の呼び方、帳票名 |
| 色、書体、余白、カード、状態色の意味 | 見出し2行、リード、現状と提案の4対 |
| ヒーロー右は「できたあとの姿」 | 役割の名前と、その人に見せる画面 |
| 主役は1つの変換（生の入力 → 提出できる成果物） | 左に置く生データ、右に置く成果物 |
| 締めは小さなPoCへの相談 | 相談時に見せてもらう現行の帳票 |
| 本文15px以上、濃色背景以外に白文字を置かない | 権限表とセキュリティ節の有無 |

現行の詳細（`CaseStudyDetailView`、`/experience/[slug]`）は別の並びである。概要、転換、指標、流れ、課題、機能、画面、技術、デモ、関連、と機能紹介が続く。この指示書の型は、その並びを次の対応で置き換える。

| 現行の詳細 | この型での置き場所 |
|---|---|
| ヒーロー（タイトル、体験ボタン、画面） | ヘッダー ＋ ヒーロー。体験ボタンはヒーローと役割デモの両方 |
| 課題からどう変わるか | 現状と提案（4対の箇条書き） |
| 利用の流れ | ヒーロー右の変換図 ＋ 中核機能の左右対比 |
| 典型的な課題、主な機能 | 4対に吸収する。機能カードの羅列には戻さない |
| 画面イメージ（スクリーンショットのギャラリー） | 役割デモ。静止画を並べるだけにしない |
| 技術・実装の考え方 | 権限表とセキュリティ。技術名詞の一覧にはしない |
| 変化の目安（前→後の数字） | 管理者画面の中の数値。ページ上部の指標帯にはしない |
| 最終CTA | 緑帯のCTA。相談先は実在するリンク |
| 関連リンク | フッターには置かない。必要ならCTAの下にテキストリンク1本 |

サイト内詳細を出している slug は `FLAGSHIP_CASE_STUDY_SLUGS`（`src/lib/content/implementation-showcase.ts`）。旗艦6本のうち、この型の基準がケア記録DX、詳細コンポーネントに乗っているのが `gempo`、`smart-agri-copilot`、`ma-dd-valueup`。`building-os` と `openestate` は外部デモが詳細リンクになっている。

## 2. ページの仕事

読者は、その業種の現場責任者か、本社で報告をまとめている人。

1ページで次の4つが分かれば足りる。

1. いま時間が溶けている作業は何か。
2. 自分の立場では、どの画面を見て、何をするのか。
3. 現場の入力が、どの書類または判断に変わるのか。
4. 次の一歩は全社導入ではなく、1〜2拠点のPoCであること。

トーンは提案である。機能名のカタログ、料金、導入実績の水増しは置かない。営業の呼びかけより「現行の帳票を見せてください」を先に書く。

## 3. 構成

上からこの順。背景は隣の節と必ず変える。推奨のリズムは、生成り → 白 → 深緑 → 白 → 生成り → 白 → 深緑。

各節に id を付ける。ヘッダーからは、デモ、中核機能、進め方、相談の4つへ飛ばせる。

### 3.1 ヘッダー（固定）

- 左: AXEONのロゴ。ロゴに社名が入っているなら、横に「株式会社」を重ねない。
- ロゴ画像は明るいヘッダーに置けるものにする。黒地ベタの書き出しは使わない。
- 右: テキストリンクではなく、pill 型のボタン1つ。「PoCのご相談」。押すとページ末の相談節へ移動し、その節のボタンは実在の相談URL（サイト内なら `/contact`）を開く。
- 途中の節へのリンクは、ボタンの左にテキストで置いてよい。ハンバーガーは作らない。

### 3.2 ヒーロー

左が文章、右が「できたあと」のカード。比率はおおよそ 1.15 : 0.85。

左に置くもの。

- 眉: 「{業種} DX 提案」。日本語。字間は広げない。
- 見出しは2行。改行は意味の切れ目だけ。1行目はその人の行為、2行目は手元に残る成果。
  - 基準: 「現場は入力するだけ」／「報告書まで自動で作成」
  - 型: 「{現場の行為}は{最小の動作}だけ」／「{成果物}まで自動でできる」
- リードは2〜3文、17px前後、幅は40字前後まで。構成は「いまの属人的な連鎖」→「一つの構造化データに集約する」→「本来の仕事の時間を戻す」。
- 「ゼロにする」と書かない。基準ページのリードは「ゼロに近づける」。画面内の説明文も同じ強さに揃える。

右に置くもの。

- カード見出しは、そのデモの変換後の流れ。基準ページは Before の3段をブランド色で塗っているが、これは引き継がない。痛みの流れは次の節に置く。
- 3段。上から「現場の入力」「仕組みが構造化する」「人が確認して確定」。最後の段だけを濃色にする。
- 見出しの2行目に `white-space: nowrap` を付けない。狭い画面ではみ出す。

### 3.3 現状と提案

見出しの型: 「"人の目と手"が律速になっている業務を、仕組みで置き換える。」業種の律速（転記、探し物、電話の再確認）に言葉を変えてよい。改行は読点か、節の切れ目。

その下は4対。左が現状、右が提案、中央に矢印。モバイルでは上下に積み、矢印は下向き。

各行は1文、同じ文法で対にする。基準の4対は次のとおり。他デモも4対に圧縮する。3対以下にはしない。5対以上にはしない。

| 現状 | 提案 |
|---|---|
| 報告の形式がバラバラで、確認に手間がかかる | 選択式・ワンタップ報告で入力を標準化 |
| 未報告・未確認が一覧で見えず、もれが起きる | 未報告・未確認・アラートを自動ハイライト |
| 報告書への手転記でミスと時間ロスが発生 | 報告から報告書ドラフトを自動生成し承認するだけ |
| 医療者との予定共有が個別連絡頼み | 看護師×医師の予定を1つのカレンダーで共有 |

左の印はバツ（警告色）、右の印はチェック（完了色）。現状側のカードは破線、提案側は実線。

### 3.4 役割デモ

見出しの型: 「立場ごとに、見える画面も権限も変わる。」

リード: 同じシステムのなかで、誰が何を見られ、何を操作できるかが違う、と1文。そのあと「タブを切り替えて確認する」または「操作するデモを開く」。

役割は2つか3つ。基準は次の3つ。

| 役割 | 画面の原則 | 見せるもの |
|---|---|---|
| 現場スタッフ | 自分の担当範囲だけ。大きなボタン。入力するだけ | スマホ枠。今日の予定、主ボタン1つ、定型入力4つまで |
| 内勤・管理者 | 全体を俯瞰。未対応だけが前に出る | PC枠。数値4つ、拠点の状態、確認キュー |
| 外部の関係者 | 社内には入らない。許可された情報だけ | PC枠。共有範囲の注意、予定、閲覧できる記録 |

他デモへの置き換え例。

- 建設: 現場監督 / 本社 / 協力会社
- 農業: 作業者 / 農場管理者 / （必要なら）出荷先
- 建物管理: 巡回者 / 管理員 / オーナー
- M&A: 現場担当 / 投資担当 / 先方

各タブの直上に1文。型は「{役割}は{見える範囲}だけ。{操作の原則}。」

画面の中で押せるものは、次のどちらかにする。

- そのページ内で、対応する成果物（次節のドラフトと同じ中身）が開く。
- そのデモの実機URLを新しいタブで開く。URLは `implementation-showcase` の体験リンクと揃える。

タブ切替だけの画面を「インタラクティブ・デモ」と呼ばない。実機があるなら、この節のリードの横に「デモを体験する」を置く。

モックに出す数値は、その節の末尾で「画面内の数値は説明用です」と1行書く。架空のプロダクトドメイン（`app.example.jp` のような実在しそうなホスト名）は置かない。アドレスバーが必要なら `demo` と役割名だけにする。

「見えない」「対象外」は薄いグレーで示す。警告の赤は、対応が必要な異常だけに使う。

### 3.5 中核機能（1つの変換）

見出しの型: 「バラバラな{入力}を、提出できる{書類}に。転記の手間を、確認だけに。」

左が生の入力、右が成果物、中央に矢印。モバイルでは矢印を下向きにする。

基準の中身。

- 左: LINE Works の自由文2通（血圧、服薬、膝の痛み）。
- 右: 看護・支援記録のドラフト。利用者、時刻、バイタル、服薬、状態、特記。機械が拾った値だけを琥珀でマークする。
- 注記: 自動生成はドラフトである。確定は担当者の確認と承認を経る。

他デモでも、この節は1組だけ。機能を並べない。左は現場が実際に残しているもの（短文、写真、音声の文字、Excelの1行）、右はその業種で提出している帳票。

入力の仕方を複数許す場合（選択式と自由文、写真と音声）は、ヒーローかこの節の前に「どちらも同じドラフトに集約される」と1文書く。

### 3.6 権限（条件付きで必須）

複数の会社、拠点、外部組織が同じデータを見るデモでは必須。一人で完結するデモでは省いてよい。省くときは、役割デモの各注記に見える範囲を書き、この節は作らない。

見出しの型: 「自分に関係する範囲しか見えない、を原則に。」

表は「機能またはデータ × 役割」。役割は役割デモより多くてよい（基準は現場、自社の専門職、内勤、外部、経営の5列）。記号は3つ。

- 全部できる
- 担当または許可された範囲だけ
- できない

凡例を表の直下に置く。読み手が驚くマス（外部が入力できる、経営は見られても承認できない、など）には、表の下に1行で理由を書く。理由が書けないマスは記号を変える。

モバイルでは横スクロールしてよい。そのとき左の機能名の列は固定する。

### 3.7 セキュリティ（条件付きで必須）

個人情報、要配慮個人情報、顧客の取引情報、建物や圃場の運用情報を扱うなら必須。

見出しの型: 「信頼を預かるシステムとして、設計する。」

先頭に前提を1ブロック。扱う情報の種類と、どのガイドラインの考え方に沿うかを書く。準拠の版が未確認なら「正式提案の前に再確認する」と書く。そのブロックは警告色にしない。警告色は障害の告知に残す。前提は生成り地に、左線だけアクセント色。

カードは4枚まで。基準は次の4つで、業種の言葉に置き換える。

1. 役割とデータの分離。関係しないデータには到達できない。
2. 誰が、いつ、何を見たか編集したかの記録。
3. 通信と保存の暗号化。端末紛失と退職時に権限を切る。
4. 同意、第三者提供、保管場所、漏えい時の連絡。

法令名をこのページで断定しない。

### 3.8 導入の進め方

見出しの型: 「いきなり全面導入ではなく、低リスクのPoCから始める。」

4段。線でつなぐ。最初の段だけ塗りつぶし、「これから始める場所」と分かるようにする。モバイルでは線を消し、番号が縦に続けばよい。

| 番号 | 期間のラベル | 見出し | 中身の型 |
|---|---|---|---|
| 01 | 2〜3週 | 業務ヒアリング | 現行の帳票と報告の実物を見て、効果が出る範囲を決める |
| 02 | PoC / 1〜2拠点 | 小さく試す | 報告から成果物までを限定して試し、前後を数字にする |
| 03 | 段階展開 | 横展開 | 効果を見て範囲を広げる。権限と連携を本運用にする |
| 04 | 継続 | 定着と改善 | 現場の声で直し、隣の業務へ広げる |

「20拠点」のように、基準ページの規模を他デモへコピーしない。そのデモの読者が持つ単位（現場数、圃場数、棟数、案件数）で書く。単位が決まっていなければ「効果を確認した範囲から広げる」と書く。

### 3.9 相談

濃い緑の帯。中央揃え。

- 眉: NEXT STEP（この1か所だけ英語でよい）
- 見出し: 「まずは、現状を見せてください。」他デモでもこの見出しを維持してよい。変えるなら「見せてほしい現行資料」が主語に残る文にする。
- 本文: 何を見せてもらうか（Excel、帳票、報告フロー）と、PoCでどの時間を数字にするか。
- ボタン1つ。ラベルは「PoCについて相談する」。リンク先は `/contact` または、そのデモ用に用意した実在の相談先。`#` は禁止。
- 帯の中の文字とボタンは、背景とのコントラストが足りる色にする。琥珀の塗りの上に白文字は置かない。

### 3.10 フッター

左にロゴ、右に1行。「{業種}の業務DX提案」。語に「サンプル」を入れない。画面が説明用であることは、役割デモの注記に書く。

## 4. デザインのルール

この型の詳細ページは、サイト本体の青（`--color-accent-primary: #26418e`）ではなく、次の色で揃える。サイト共通ヘッダーの中に埋め込む場合も、詳細本文はこの色に合わせ、途中で青のカードへ戻さない。

### 4.1 色

```css
--ink: #1C2522;
--ink-soft: #5A6660;
--ink-faint: #8B958F; /* モックの補助ラベルだけ。説明文には使わない */
--paper: #F6F4EE;
--surface: #FFFFFF;
--surface-2: #EDF1EC;
--primary: #175E51;
--primary-d: #0F4438;
--primary-soft: #DBE9E3;
--accent: #DE8E33; /* マーク、未対応、矢印。ボタンの塗りは下の条件を満たすときだけ */
--accent-soft: #FAEAD2;
--line: #E3E0D6;
--alert: #BE5239; /* 対応が必要な異常、現状のバツ */
--ok: #3B8C6C;
```

色の意味は一つに固定する。

- 深緑は、ブランド、主操作、変換後の最終段。
- 琥珀は、注目と未対応。CTAを琥珀で塗るなら、文字は `#1C2522` か `#0F4438`。白は置かない。
- 赤は異常と、現状側の否定。非表示や権限なしに赤を使わない。
- 完了の緑は、報告済、チェック、有効。
- 痛みの工程を深緑で塗らない。

明い背景の本文は `--ink` か `--ink-soft`。白文字は、深緑の塗りの上だけ。

### 4.2 文字

- 本文: Noto Sans JP。説明文は 15px 以上。ヒーローのリードは 17px、相談の本文は 16px。
- 見出し: Shippori Mincho。ページの h1 はおおよそ 34〜58px、節の h2 は 26〜40px。行の高さは見出し 1.35 前後、本文 1.75 前後。
- ラベル、番号、時刻、拠点コード: Roboto Mono。眉を日本語で書くときはゴシックのままにし、字間 `0.22em` や大文字化を付けない。
- 見出しは `word-break: keep-all`。折り返すときは `<br>` か行の配列で、意味の切れ目だけを指定する。`max-width: 14em` のような文字数幅で末尾1〜2文字を落とさない。
- 和文を italic にしない。
- モック内部の補助ラベルは 12px まで。9〜11px の予定名や注釈は作らない。

### 4.3 レイアウト

- 本文幅 1080px、左右 24px。
- 節の上下は PC 96px、900px 以下は 64px。区切りはこの1本でよい。それより狭い端末用に、はみ出す部品だけ個別に直す。
- 角丸は、ページの大カード 16〜20px、モック内の小カード 10〜14px、pill は全丸。スマホ枠は外側 30px、画面 21px。
- 影は2段まで。通常カードと、ヒーローまたはデモ枠の強い影。
- 半透明のガラス背景は使わない。枠線は `--line`。
- デモ節だけ画面幅いっぱいの深緑。その中のアプリ枠は白。

### 4.4 部品

このページで使ってよい部品は次だけ。新しいカード種を増やさない。

- 眉と、その左の短い線
- 3段のフローカード
- 現状 / 提案の2カラムと中央の丸矢印
- 役割タブ（選択中は白地に深緑の文字）
- スマホ枠、PCのウィンドウ枠
- 数値カード4枚（完了、未対応、要対応、累計）
- 状態 pill（完了、待ち、要対応、対象外）
- 左の生入力と右の帳票、中央の矢印
- 権限表
- セキュリティの前提バーと4カード
- 4段の番号と線
- 相談帯の pill ボタン

状態 pill の言葉はデモごとに変えてよい。色の割り当ては変えない。

### 4.5 動きと操作

- タブ切替のフェードは 0.35秒まで。`prefers-reduced-motion: reduce` ではフェードもスムーススクロールも止める。
- タブはボタンにする。選択中は `aria-selected`、パネルは `aria-controls` で結ぶ。
- モック内の主操作は `button` かリンク。`div` にクリックだけ載せない。
- 装飾のSVGには `aria-hidden="true"`。

## 5. コピーを書く手順

1. そのデモの実機を開き、現場が最後に手を離す成果物を1つ決める。ケア記録DXなら看護・支援記録のドラフト。
2. その成果物ができる前に、人が手でやっている確認と転記を4つ書く。
3. 見出し2行を、行為と成果物で書く。
4. 役割を2〜3人に分け、各人の画面に出る固有名詞（拠点、利用者、案件）を3件だけ作る。同じ名前を、現場画面、管理者キュー、帳票ドラフトで揃える。基準では「田中 様」「さくらホーム」「10:00」が現場と帳票で一致している。
5. 権限表を埋める。説明できないマスは空のまま公開しない。
6. 相談文に、見せてほしい現行資料の名前を入れる。
7. 体験カードのキャッチコピー（`implementation-showcase` の `catchCopy`）と、詳細の見出し1行目を同じ約束にする。ショーケース側が「話すだけ」、詳細が「タップだけ」のように分けない。音声が実機にあるなら、詳細の役割デモにもその画面を置く。

文章量の上限。

- ヒーローのリード: 120字前後

## 7. 基準ページからの引き写し禁止

`/lp/kaigo-care-dx` を見た目の基準にしてよい。次は欠陥なので、他デモへコピーしない。同じページを直すときも閉じる。

- 相談ボタンの `href="#"`。
- フッターの「サンプル」。
- ヒーロー右が Before なのに、手転記の段を深緑で塗っていること。
- 見出しハイライトの `nowrap`。
- 日本語の眉に `letter-spacing: 0.22em` と `uppercase`。
- 白文字の琥珀ボタン。
- タブ以外が動かないのに「インタラクティブ・デモ」と書くこと。
- 実機（ケア記録DXなら `implementation-showcase` の外部デモ）へのリンクが無いこと。
- 「非表示」を要対応と同じ赤にすること。
- 説明本文の 13px 台、カレンダー予定の 10px 前後。
- セキュリティと次の節が同じ白で続き、境目が消えること。
- 黒地のロゴを生成りヘッダーに置くこと。
- 外部の医療者が報告入力できる、のような、注釈の無い権限マス。
- `prefers-reduced-motion` が無いこと。
- メタ情報が title だけのまま公開すること。説明文は 120字前後で書く。

## 8. 完成チェック

- 上から読んで、作業の痛み、自分の画面、成果物、PoCの順に答えがある。
- ヒーロー右と中核機能が、同じ成果物を指している。
- 役割デモの固有名詞が、帳票ドラフトと矛盾しない。
- 体験カードの約束と、詳細の見出しが同じ動作を言っている。
- 相談ボタンとデモボタンの両方が、実在のURLを開く。
- 本文を15px未満にしていない。白文字は深緑の上だけにある。
- 900px幅と 375px幅で、見出し、スマホ枠、権限表の左列が画面内に収まる。
- 隣り合う節の背景が同じ色でない。
- 「サンプル」「ゼロにする」「インタラクティブ」の語が、中身と一致している。一致しない語は削除する。
