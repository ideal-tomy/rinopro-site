# AXEON スクロール不具合：調査結果と改善計画

作成日：2026-10-13。元指示：[AXEON-support-scroll-fix.md](./AXEON-support-scroll-fix.md)。

## 結論

対象は `/services/insourcing-enablement`（半内製化/FDE）。「支援を始める前に」は `#checks` にある。`/about` や `/services/consulting` の相談例ではない。

現在の実装は、セクション単位の演出へ統一できていない。共通の `ScrollRevealController` によるセクションの縦移動と、`useScrollReveal` によるカード個別の縦移動が同居する。SPでは後者だけCSSで止めており、親の演出は残る。速度や移動量だけを調整しても、この構造は解消しない。

優先する修正は、**対象ページをSSR時点から共通の自動演出対象外にし、ページ専用処理で各セクションを1回だけopacity表示すること**。横スクロールと反転は別の要素に担当させる。

今回行ったのは調査と計画作成。アプリの実装は変更していない。先行タスクの未コミット変更も保持している。

## 確認した事実

ローカル本番ビルドの `http://127.0.0.1:3104/services/insourcing-enablement` をChromeとPlaywright WebKitで調査。390pxと1440px、通常モーション設定で記録した。

証拠：[evidence.json](archive/support-scroll-investigation-2026-10-13/evidence.json)、[初期化完了待ちの追加計測](archive/support-scroll-investigation-2026-10-13/hydrated-evidence.json)。再実行：[調査スクリプト](./AXEON-support-scroll-investigation.cjs)。

### 1. 親の縦移動が実際に残る

Chromeの390pxで、`#checks` 自体にWAAPIの `translate: 0 18px → 0 0`、980msを記録した。1440pxではChrome/WebKitとも760msの同じ親演出を記録した。

カード側を `translate: none !important` にしても、親の移動による画面座標の変化は消せない。横スクロールの途中に親の演出が進めば、カード全体が縦に動いて見える構造は残っている。

### 2. PCではカード個別の移動も残る

1440pxのサンプルに、事前確認カードの個別 `translate` と実行中のCSS Transitionを記録した。カードのdocument上端はChromeで約1281.32〜1296.88px、WebKitで約1286.70〜1292pxの範囲を動いていた。これは表示途中の動きであり、「演出完了後の永続的なレイアウト崩れ」の証明ではない。

### 3. 初期化タイミングに依存する登録経路がある

共通controllerは最初に演出対象を `tracked` に登録する。一方、専用hookの除外目印 `data-reveal-ready` はクライアントのref実行後に付く。

`scan()` は `tracked.has(element)` を先に判定してスキップする。そのため、共通controllerが先に登録した親は、後から子に専用処理の目印が付いても登録解除されない。調査では初期属性のないsectionと、後からreadyになったカード、親WAAPI演出の同居を確認した。追加計測でも専用初期化を待った後のスクロールで親演出が発生したため、単に操作開始を遅らせる対応では解決しない。

登録順序の厳密な時系列（両effect/refの実行時刻）はまだ計測していない。競合の経路はコードから確認できるが、その発生頻度や全症状との因果は追加検証する。

### 4. 操作後だけ安定する理由になり得る処理

共通controllerの `focusin` 処理は、対象または登録済み祖先のWAAPI演出をcancelする。位置ボタンへフォーカスが移ると、未操作の場合と親演出の状態が変わる可能性がある。

ただし事前確認カードの `li` 自体にはクリック処理・反転処理・tabIndexはない。「カードをタップ」と「下部位置ボタンをタップ」は分けて再現し、両者を同じ原因と断定しない。

### 5. 今回再現していない部分

390pxでは横スクロールを直接動かした後とカードクリック後に、カード5枚のdocument上端・高さの差は0だった。trackの `scrollTop` も計測サンプルで0。カードの再マウント、横移動による自然高さの変化、画像読み込みによる高さ変化は今回確認していない。

今回の横移動はDOMの `scrollTo` を用いた計測であり、指のスワイプ再現ではない。また初回サンプルはセクション入口を計測したもので、横移動時に必ず親演出が実行中だったことまでは保証していない。ユーザー報告の全操作経路を完全に再現できた扱いにはしない。

WebKit390pxでは親WAAPIログが出なかった試行もあった。この結果も、全条件で同じ演出が実行されていないこととして保存する。iPhone Safari実機は未確認。

## 改善の実装計画

### P0：再現条件と測定を固定する

1. 現在の未コミット変更とブランチを記録し、相談例の先行変更を保持する。
2. 初回ロード直後・専用初期化後・低速CPU/ネットワークの3条件で同じ操作を実行する。
3. `Element.animate`、CSS Transition、data属性変更、focusin、card DOMの接続状態を時刻付きで記録する。親子のどちらが動いているか、先に登録されたのはどちらかを判定する。
4. カードごとの `rect.top + scrollY`、trackに対する相対top、高さ、trackのscrollLeft/scrollTop、ページscrollYをフレーム単位で保存する。ページの縦スクロールをカード自身の縦ずれと誤認しない。
5. 静止画に加え画面動画または連続フレームを保存する。CLSだけではtranslateの見た目のずれを判定できない。

### P1：演出の担当をページ専用に一本化する

変更候補：`EnablementPage.tsx`、`enablement-page.module.css`。専用hookが必要なら `useEnablementSectionReveal.ts` を追加する。

- ページのルートへ `data-scroll-reveal="off"` を宣言的に付ける。SSR HTMLに含め、共通controllerが初期スキャンで親子を登録しないようにする。クライアントで後から追加する方式は避ける。
- `checksReveal` と `supportReveal` の子セレクターを撤去し、セクションの外側ラッパーだけを観測する。
- 見出し・説明文・一覧を同時に表示する。カード・図解・本文に二段目の遅延を付けない。
- 表示はopacityのみ、600ms、delayなしを出発点にする。縦移動が必要な場合も外側ラッパーに限定し、最大8px。まずopacityのみで不具合経路を検証する。
- 表示後は `entered` を保持しunobserveする。横移動・位置更新・フォーカス・タップで表示状態を書き戻さない。
- SPの「カードだけ演出なし」という上書きは、単一演出へ移行した後に不要部分を削除する。共通CSSや他ページの演出速度は変更しない。
- reduced-motionでは最初から表示し、実行中に設定を変えた場合も即座に表示・停止する。
- JavaScript無効・初期化失敗・IntersectionObserver非対応でも本文を読める設計にする。SSRでopacity:0にしない。初期化後に隠す設計を採る場合は可視要素を隠し直さず、タイムアウト等の復帰条件を明示する。
- 共通controllerが対象ページを除外した影響を棚卸しする。Heroは初期表示、checks/support/development/問い合わせは適切な外側単位で1回だけ表示。開発セクション内の長いタイムラインは外側のopacityだけにし、反転・デモ再生はその内部で維持する。

共通controller自体の変更は第一案では不要。既存の `data-scroll-reveal="off"` を利用して対象ページへ限定する。共通の `tracked` 再評価を追加する案は、他ページへの影響が広いため今回の第一案にしない。

### P2：横スクロールを表示演出から完全に独立させる

変更候補：`EnablementPreSupportCards.tsx`、`enablement-page.module.css`。

- ネイティブ横スクロールと現在の5件の内容・図解を維持する。新しいライブラリは追加しない。
- track/cardに表示用translate・transform・opacityアニメーションを付けない。横移動はscrollLeftだけにする。
- `touch-action: pan-x pan-y` を維持する。preventDefaultを用いた縦操作の一律禁止は追加しない。
- flex stretchによる等高表示と図解の確保領域を維持する。巨大な固定カード高さを追加しない。SVG主体の図解と別セクションのImageを区別する。
- indexは実際のスクロール位置を基準に同期する。`setIndex(clamped)` の先行更新で、smooth移動中に現在位置が往復するかを計測し、必要ならscrollイベント由来の確定状態へ寄せる。
- カード幅+gapの丸め、終端の最大scrollLeft、1099/1100px切り替え、リサイズ時の現在位置を確認する。ここは縦ずれの確定原因ではなく位置同期の検証項目。
- 位置ボタンは見た目の2pxバーを保持しても、操作領域は44px程度を確保する。tablist/tabの意味と実際のpanel構造が一致しない現状は通常のbutton＋aria-currentへ整理する候補。本文内容や新しい操作は増やさない。
- 事前確認カードに反転機能を追加しない。「開発の進め方」の既存反転機能は削除しない。

### P3：対象ページ内の周辺整理

元指示の残件をスクロール修正と混同しない。

- `#approach` の独立した「支援の進め方」は現在も存在する。元指示に従う実装では、このセクションを削除対象として明示し、stagesデータ・専用reveal・参照リンク・余白を整理する。
- `#development` の「開発の進め方」は別セクション。似た見出しという理由で削除せず、反転・タイムラインを維持する。
- 調査したEnablement関連ファイルには「月額」「3か月」「3ヶ月」「更新」の該当説明を検索で検出しなかった。ただし今後の実装で描画本文・裏面・埋め込みデータを含む対象ページ全体を確認する。期間に関する全サイト一括置換は行わない。

今回のユーザー依頼は調査・計画のため、これらの削除はまだ実行しない。

## 再現・受け入れ検証

| 観点 | 検証条件・合格条件 |
|---|---|
| 幅 | SP375/390/430、タブレット768/1024、横並び境界1099/1100、PC1280/1440 |
| 経路 | 再読込→上から縦スクロール→演出中に横移動→完了後に横移動→カードタップ→位置ボタン操作→前後移動→離れて戻る |
| 実入力 | Chrome CDPタッチ模擬操作、マウス/トラックパッド、キーボード。DOM scrollToだけで合格にしない |
| 縦位置 | ページ縦移動を補正したcard/track相対topの変動が1px以下。高さの変動も1px以下。意図的な外側演出がある場合はその変位を別記録 |
| 初回表示 | 親子の同時重複演出なし。セクション内の別遅延なし。横操作中の隠し直し・演出再実行なし |
| タップ差 | 未タップ、カードタップ、位置ボタンタップの3経路で位置と高さが同じ。focusinのcancelに安定性を依存させない |
| 縦スワイプ | 横track内から始めた縦ジェスチャーでpage scrollYが変化。track scrollTopの変化による見かけの成功にしない |
| 再表示 | 離れて戻ってもenteredは保持。visibleな本文を再び透明にしない |
| 切替・終端 | 全5件へ到達、現在位置と実カード一致、幅変更後の位置・高さ安定 |
| 動きを減らす | 初期reduceと表示途中の切替、どちらでも全文を即表示。横操作は維持 |
| 機能維持 | 開発の反転・再生/停止、問い合わせリンク、ページ内リンク、前後のセクションを確認 |
| ブラウザ | ChromeとPlaywright WebKitを別記録。iPhone Safari実機の縦/横スワイプは独立した確認項目 |

修正後は対象TSXへのESLint、`npm run build`、`git diff --check` を実施する。ビルドとdevで同一生成ディレクトリを同時更新せず、検証用プレビューのビルド・ポート・コード版を固定する。
