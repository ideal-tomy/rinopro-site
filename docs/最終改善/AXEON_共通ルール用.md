# AXEON｜全ページ共通デザインシステム・制作仕様書

> **リポジトリ内の運用正本:** 実装・レビューの判断は [`AXEON_UI共通ルール.md`](./AXEON_UI共通ルール.md) を優先する。本書は外注・合意・依頼文テンプレを含む詳細版として残す。

**版:** v1.0 ― 外注・設計合意用／未承認の提案値を含む  
**作成日:** 2026-10-16  
**対象:** AXEONサイトに含まれる**すべての公開ページ、サービスページ、業界別LP、動的ページ、独立HTML、デモ紹介・体験画面、問い合わせ等**  
**方針:** **個別ページごとに改善・完成させる方式は採用しない。全ページを共通デザインシステムの適用対象とし、共通仕様を先に確定させる。**  
**目的:** 文字組み・色・余白・コンテナ・枠・図解・レスポンシブ・品質検証を一貫した仕様として管理し、「ページによって品質・見た目・改行が異なる」「直すたびに別ページが崩れる」を防ぐ。

> **この文書を渡すだけで実装を開始しないこと。** 以下には既存ソースで確認された値、UP Forwardの実測値、およびAXEON向けの設計提案がある。区別を維持し、デザイン担当者によるサイト共通の承認後、実装すること。
>
> **「共通化」≠「全ページを同じカード・同じ行間・同じ構成にする」。** *意味が同じ要素は同じ役割・基準で表示し、内容の異なる区画では承認済みの複数の表現方法を使い分ける*、という意味である。

## 1. 共通デザインの方針（全ページに適用）

1. **読みやすさを優先。** 通常本文は濃い文字色と16pxを基準とする。薄いグレーや小さい文字で情報の優先順位を表現しない。
2. **文字の役割で区別。** Hero、セクション見出し、項目見出し、リード、通常本文、補足、UIラベルには別々の明確な仕様を用いる。「全テキスト同じ行間」は採用しない。
3. **装飾ではなく内容を見せる。** 文章、図解、比較、画面サンプル、写真、タイムラインなどの中から目的に適した形式を選ぶ。全区画をカードで覆わない。
4. **スマホも独立した完成画面。** PC版を単に縦積み・縮小した状態を完成としない。
5. **全ページを同時に規格へ統合。** 個別ページを試験対象にしたり、改善済みページから順番に移植したりする進行は採用しない。設計承認は**全体の共通部品と表現パターン**に対して行う。
6. **共通基盤は一本化。** CSS変数、フォント読み込み、共通コンテナ、文字の役割、背景と文字の組み合わせ、主要コンポーネントはサイト全体で管理する。
7. **ページの特徴は残す。** 全ページが同じ見た目にならないよう、共通基盤の上で承認済みの表示バリエーションを選ぶ。別テーマ・独立HTMLにも共通の読みやすさ／表示品質基準を適用する。

## 2. 全サイトの適用範囲と例外管理

### 2.1 対象区分

| ページ区分 | 例 | 必ず共有するもの | 認める表現上の違い |
|---|---|---|---|
| 企業・案内 | トップ、会社紹介、サービス総合、問い合わせ | 基本文字・余白・枠・リンク・コンテナ・レスポンシブ品質 | Hero、写真、ブランド演出 |
| サービス | コンサルティング、半内製化等 | 同上＋比較・工程・資料紹介の共通表現ルール | 各サービス固有の図解 |
| 業界別・記事 | `/industries/[slug]`、記事、事例 | 本文・見出し・引用・表・図版の文字組み | 業界に必要な実写／図解、記事の読み幅 |
| LP・独立HTML | `/lp/kaigo-care-dx`、他の静的LP | 本文の可読性、枠、余白、操作性、検証条件、共有設計トークンへの接続 | **承認済みテーマ**の色・ディスプレイ書体・コンテンツ表現 |
| デモ・業務画面 | `/demo/[slug]`、`/experience`、見積もり導線等 | 色の意味・文字階層・最小可読性・操作・端末適応 | 高密度UIに必要な個別レイアウト／状態表示 |

**例外はページ名をキーにして場当たり的に作らない。** 「本文密度：standard/compact」「テーマ：corporate/care」「図表：responsive/scrollable」といった**意味を持つ共通バリエーション**で指定する。例外表には理由・所有者・検証方法を記録する。

### 2.2 必須の全ページ台帳

実装に入る前に、以下の情報を持つ**公開URLの全件一覧**を作成する。Next.jsの静的ルートだけでなく、動的スラッグ、独立HTML、問い合わせ・見積もり・デモ、ナビに出ないURLも対象。

`URL / ページ種別 / テーマ / 利用CSS / 利用フォント / 対応する共通部品 / 図表形式 / PC-SP特記事項 / 検証状況 / 例外理由`

非公開・認証が必要な画面はテスト方法を別記し、テストできない状態を「合格」としない。

## 3. 文字表示システム（共通・提案値）

**状態:** 以下の値はAXEON向けの設計初期値。**[提案・要承認]**。画面カンプと実際の日本語原稿で検証し、共通ルールとして一度に承認する。

### 3.1 書体の役割

| 役割 | 共通候補 | 指定方針 |
|---|---|---|
| 日本語本文・一般見出し | `Noto Sans JP`, `Hiragino Sans`, sans-serif | **日本語の標準系列を1つに定める**。必要な400/500/700ウエイトを正しく供給 |
| 英数字のUI表示 | 同じ本文系列、必要なら既存`Geist` | 原則は本文の表示に合わせ、英数字だけ不自然に異なる字面にならないよう検証 |
| 大きなディスプレイ見出し | 原則は日本語標準系列。**共通のdisplay-serifバリエーション**のみ任意 | 介護DXの明朝体は「選択できる表現例」。全Heroへ強制しない |
| 数字・短い英字ラベル | 標準系列または承認済みのmono系列 | 装飾ラベルと長文の役割を分ける |

**現行コードの注意:** `src/app/layout.tsx` のNoto Sans JPは400のみの読み込み設定。太字表示が意図したウエイトかRendered Fontsで確認し、必要なら読み込み方法を変更すること。

### 3.2 役割別タイポグラフィ

| 共通ロール名 | PC 1280–1440px | SP 320–430px | 太さ案 | 利用条件 |
|---|---|---|---|---|
| `display` | 48px / 1.30 | 32px / 1.35 | 700 | Heroの主要コピーのみ。長文には使わない |
| `page-title` | 40px / 1.40 | 30px / 1.40 | 700 | ページ全体の主見出し |
| `section-title` | 34px / 1.45 | 26px / 1.45 | 700 | セクション単位の見出し |
| `item-title` | 22px / 1.45 | 19px / 1.50 | 700 | 項目・業務・比較対象の名称 |
| `lead` | 18px / 1.75 | 16px / 1.75 | 400–500 | 要旨を示すリード文 |
| `body` | 16px / 1.75 | 16px / 1.70 | 400 | 標準本文。サイトの基本サイズ |
| `supporting` | 14px / 1.65 | 14px / 1.65 | 400–500 | 注釈、図版キャプション。**主な説明文には使わない** |
| `ui-label` | 13px / 1.45 | 13px / 1.45 | 600–700 | ボタン補助、フィールド名、短いラベル |
| `eyebrow` | 12px / 1.40 | 12px / 1.40 | 700 | 英字などの短い装飾ラベル。重要な説明に使わない |

**デモ・帳票の例外:** 密度の高いUIの数値や表ラベルなどが上表に入らない場合は、意味別の`data-dense`等の共通バリエーションを設計し、**画面名だけを理由に個別数値を乱立させない**。例外でも視認性と操作性を検証する。

**見出しレベルと見た目は混同しない。** `h1`/`h2`/`h3` は文書構造に基づき決め、`display`/`section-title` 等は見た目のロールとして指定する。見出しの階層をCSSの都合で変更しない。

### 3.3 文字色・背景色

| セマンティックトークン | 提案値 | 用途 |
|---|---|---|
| `text-heading` | `#111827` | 見出し・重要な論点 |
| `text-body` | `#1F2937` | 普通の本文。**薄灰色禁止** |
| `text-supporting` | `#475569` | 補助説明。本文と混同しない |
| `link` | `#1D4ED8` | リンク／明確な操作 |
| `brand-primary` | `#26418E` | AXEONのブランド青。ボタン・短い強調に使用 |
| `surface-page` | `#FAFAF8`（現行コードの候補） | 基本背景。白区画との切替はルール化 |
| `surface-card` | `#FFFFFF` | 情報をまとめる必要がある場合 |
| `border-subtle` | `#E5E5E0`（現行コードの候補） | 必要最小限の区切り |

暗色背景、写真上、テーマ付きLPでは、**背景と文字色を対で定義**する。色を「薄くして控えめ」にするのではなく、文字サイズ・余白・配置で情報階層を示す。

**合格条件:** 通常文字の背景に対するコントラスト比は原則4.5:1以上。大きな文字はWCAG相当の条件に応じて3:1以上。ボタン文字・入力・選択・無効状態・グラフの判別も確認し、色だけで情報を伝えない。※数値は可読性の最低条件であり、見た目の良さを保証するものではない。

### 3.4 日本語の改行・文章幅

1. **1段落は通常、1つの連続した文字列。** 表示を整える目的だけで文字列を配列に分割し、各`span`を`display:block`にしない。
2. **通常本文に装飾目的の`<br>`を入れない。** 段落が変わるなら`<p>`を分ける。短いHeroコピーなど明確な意図があるものだけ例外許可する。
3. `word-break: keep-all` / `white-space: nowrap` を日本語見出しや本文全体に一律適用しない。必要な固有名詞・数値単位だけ範囲を限定する。
4. 1〜2文字の孤立行や極端に短い行が出たとき、**先に親コンテナ幅・余白・Grid/Flexの`min-width`・フォント実寸を点検**する。文言を勝手に改変して隠さない。
5. 文章専用の長い読み物には適切な行長を設けるが、**すべての本文を固定幅の狭い箱にしない**。二列＋図解では、文字列のコンテナ幅に合理的な根拠が必要。
6. 見出しを手動改行する場合は、320 / 375 / 390 / 430 / 768 / 1280 / 1440pxで破綻しないこと。PCとSPの改行を完全一致させる必要はない。
7. 和文の読点・句点・助詞の直前直後で不自然な折り返しがないかをブラウザ画像で確認する。**機械判定だけで「自然な改行」を保証したと扱わない。**

**実装上の推奨:** HTMLの自動折り返しを基本とし、必要に応じてロール専用の`text-wrap`等を検討する。CSSの一律グローバル強制指定や`!important`は増やさない。

## 4. 余白・コンテナ・整列（共通・提案値）

### 4.1 共通Spacing

**[提案・要承認]** `4 / 8 / 12 / 16 / 24 / 32 / 48 / 64 / 80 / 96` pxを主要な距離の候補とする。ただし**数値を使用してよい箇所は役割で定義**し、機械的に全要素へ均等適用しない。

| 共通ロール | PC | SP | 意味 |
|---|---:|---:|---|
| `section-standard` | 上下96px | 上下64px | 通常区画の切り替わり |
| `section-compact` | 上下64px | 上下48px | 関連性の強い連続区画 |
| `heading-to-lead` | 24px | 16px | 見出しと要旨 |
| `heading-to-content` | 40px | 28px | 見出しから主な図・一覧へ |
| `item-title-to-body` | 12px | 8–12px | 同じ内容単位 |
| `paragraph-to-paragraph` | 16px | 16px | 通常段落間 |
| `content-group` | 32–48px | 24–32px | 別の論点・図表・結果のまとまり |

- 見出し・本文の`margin`はリセットしてよいが、**距離は親レイアウトの`gap`等で役割別に決める**。
- 背景を大きく切り替える区画やHeroは、役割に応じた専用の*共有バリエーション*を持つ。すべてを96pxに揃えない。
- 余白の大小は情報のまとまりで決める。**他のページで同じ数字を使うためだけに、不自然な空白を作らない**。

### 4.2 コンテナ幅

**[提案・要承認]**

- `container-wide`: 最大1160px。標準の情報配置、ヘッダー、フッター、図解等。
- `container-reading`: 読み物・長段落向けの可読幅。内容に応じて`ch`基準で設計。カード内・比較内には強制しない。
- ページ左右のガター：PC40px程度／タブレット32px程度／スマホ20px程度を初期値にする。
- コンテナの左右端はヘッダー・本文・CTA等で**意図なくずれない**。全面出血（full-bleed）の背景は可、内部本文の基準位置は共通。
- 一律の`max-width`と左右paddingが二重にかからないよう、親子コンテナの責任範囲を明確にする。
- Grid/Flexの子要素には必要に応じ`min-width: 0`等を指定し、**横はみ出しの原因そのものを直す**。

## 5. パネル・カード・枠・アイコン（共通）

- **視覚的なカード枠は原則1階層。** 例えば「外側の角丸枠＋内側の角丸枠＋別の装飾枠」という意味のない重ね方は採用しない。DOMの`div`入れ子は問題ではない。
- 本文と小見出しを並べるだけなら、**まず枠なしのレイアウト**を検討する。情報のまとまりを示す必要がある場合だけ背景／罫線／カードを使う。
- 薄い影、強い影、角丸、境界線は**役割ごとの共通部品**として管理。ページごとに好きな形を増やさない。
- アイコンは識別・操作・状態説明が目的。**各項目に同じアイコンを付けただけで「図解がある」扱いにしない。**
- 見出し・ラベル・番号・カード背景をすべて強調しない。**視覚上の主役は1つ**を基本とする。
- 同じ種類の情報は共通部品を用いるが、**異なる種類の情報を、同じカード型に押し込まない**。

### 5.1 承認する共通「表現パターン」

コンポーネントライブラリとして、以下を**ページ非依存の役割**で定義し、必要なものを選んで使う。全ページへの機械的な全挿入は禁止。

| 表現パターン | 適した内容 | PCの基本 | SPの基本 |
|---|---|---|---|
| `EditorialIntro` | 大見出し＋短い要旨 | 文字とビジュアルを役割別に配置 | 見出し優先、図版と要旨の順を再設計 |
| `BeforeAfter` | 現状と改善後の対比 | 両者を見比べられる配置 | 対応する1セットを切らずに表示 |
| `ProcessFlow` | 工程・手順・流れ | 関係の見える図 | 文字の読めるステップ表示へ組み替え |
| `DecisionComparison` | 複数の選択肢と判断材料 | 表や軸、比較図 | 選択肢を照合できる構造。必要なら局所スクロール |
| `ProductScreen` | 実際の操作・出力内容 | 画面を主役にし、文章は補足 | 文字が読める範囲を見せ、詳細を切り替える |
| `Evidence` | 成果物・事例・数字 | 根拠の図版・実例が主役 | 注釈と数値が小さすぎない表示 |
| `Prose` | 長い説明・記事 | 可読幅に制限した文章 | 全幅の読める文章・自然な段落 |
| `ContactCTA` | 問い合わせ誘導 | 目立つボタンと短い補足 | 押しやすさ・文言・余白を優先 |

**介護DXページの採用ポイント:** 「文章→文章→文章」の反復ではなく、テーマに合った表現パターンを選んでいる。**これをサイト共通の制作判断にする**。参照LPの緑・明朝体・背景を一律に広めるわけではない。

## 6. レスポンシブと図解（全ページ共通）

1. PC版・SP版を**それぞれ完成画面として**設計する。PCの段組みを縦積みにするだけでは読みにくい要素がある場合、情報表現を変える。
2. スマホで読ませる文章を含むSVG・画像を単純縮小しない。必要なら文章をHTMLへ分離し、図を簡略化する。
3. 横スクロールは**表やタイムラインなど、比較のために必要な要素内でのみ**採用し、操作可能性を明示する。ページ全体の意図しない横スクロールは禁止。
4. 画像・図版は原則コンテナ内に収める。縦横比・文字の読める寸法・トリミングの優先順位を共通仕様にする。
5. スマホの本文列に不自然な右余白を作らない。必要な本文幅はコンテナ／ビジュアルの関係から決定する。
6. タッチ要素の大きさ、フォーカス表示、モーション低減（`prefers-reduced-motion`）をサイト横断で扱う。
7. ブレークポイントは適用する**意味と責任コンポーネント**を一覧化する。単純に「2個まで」に固定しない。重複する定義・打ち消しの連鎖は整理する。

**共通検証幅:** 320 / 375 / 390 / 430 / 768 / 1024 / 1280 / 1440px。必要なら1920pxも追加する。Safari（実機または適切な検証環境）・Chromeの表示差も確認する。

## 7. CSS・コンポーネントの共通管理方針

### 7.1 「単一の管理元」を作る

以下の機能ごとに**正となる管理場所を1か所**定義する。ファイル名・実装方式は既存アプリのビルド環境を確認して最終決定する。

1. **デザイントークン**：色、書体、役割別サイズ／行間、余白、コンテナ、角丸、影、フォーカス色。
2. **テキスト表示ロール**：`display`, `page-title`, `section-title`, `item-title`, `lead`, `body`, `supporting`, `ui-label`。
3. **共通レイアウト**：コンテナ、セクション、分割、比較、図版。
4. **共通部品**：ボタン、リンク、タグ、カード、入力、表、共通ナビ、CTA。
5. **テーマ・バリエーション**：corporate、care等。意味に従うテーマだけを許可し、ページURL名による場当たり上書きをしない。

### 7.2 実装上の注意（現行Next.js＋独立HTML）

- `src/app/globals.css`、Tailwind CSS 4、CSS Modulesの**優先順位と競合を監査**してから統合する。
- `!important`による全タグ指定（現在の全段落行間など）は、依存箇所を把握して移行計画を立てたうえで撤去。**単純な一括置換をしない**。
- `text-base`など既存のTailwindユーティリティとローカル定義を混同しない。独自設計トークンは衝突しにくい接頭辞（例：`--ax-*`）とする。
- 原則は意味別の共通コンポーネントを呼び出し、**同じ文字色・余白・書体をページ固有CSSで再定義しない**。
- Next.jsの共通CSSは`public/lp/*.html`へ**自動では反映されない**。独立HTMLも共通CSSを読み込めるよう、**共有スタイルの配信経路を設計**する。1つのソースから生成・配信する方式などを検討し、**手編集のCSSをNext.js用／HTML用に二重保守しない**。
- `/lp/kaigo-care-dx`の別テーマは、共通のタイポ役割・可読性・操作・余白ルールに接続しつつ、承認されたテーマトークンで表現差を維持する。
- CMS・記事のHTMLやMarkdown、動的ルートにレンダリングされるテキストにも共通の文字ロールを適用する。固定ページだけ揃えて完了としない。

### 7.3 CSS設計イメージ（**提案であり、そのまま実装する完成コードではない**）

```css
/* ロールの値はデザイン承認後に確定。接頭辞により他のCSSと衝突を避ける */
:root {
  --ax-font-body: 'Noto Sans JP', 'Hiragino Sans', sans-serif;
  --ax-text-heading: #111827;
  --ax-text-body: #1f2937;
  --ax-text-supporting: #475569;
  --ax-color-primary: #26418e;
  --ax-font-size-body: 1rem;
  --ax-line-height-body: 1.75;
}

/* 全p・liを!importantで上書きしない。意味別ロールを使う */
.ax-body-text {
  font-family: var(--ax-font-body);
  font-size: var(--ax-font-size-body);
  line-height: var(--ax-line-height-body);
  color: var(--ax-text-body);
}

@media (max-width: 640px) {
  :root { --ax-line-height-body: 1.7; }
}
```

共有CSSの実体と適用クラスの命名は、**全ルート／コンポーネントの対応表を完成させてから**確定すること。

## 8. 導入工程：全ページ横断で進める（個別ページ方式は廃止）

### フェーズA｜全資産・全ルート調査（コード変更なし）

- 公開URLの全件台帳を作成する。動的ルート・独立HTML・デモ・フォームも対象。
- フォント、色、見出し、本文、ボタン、コンテナ、ブレークポイント、装飾、独自テーマの**実使用箇所を全ページ横断で棚卸し**。
- 必要な情報表現パターンを統合し、重複／未使用のCSSとコンポーネントを判定する。
- 直すべき不具合を「共通原因」「個別のバグ」「意図された例外」に仕分ける。
- **成果物:** 全ページ台帳、競合マップ、共通化できる範囲と破綻リスクの報告。ここでまず見積もりを出す。

### フェーズB｜全サイト共通のデザイン仕様を決定（コード変更なし）

- 本書の提案値を基に、フォント・文字色・行間・余白・コンテナ・枠・共通表現パターン・承認済みテーマを定義する。
- **ページ単位の完成カンプではなく、各ロール／コンポーネントのPC・SP実寸サンプルをまとめた共通デザイン仕様（Figma等）**を提示する。文章は実際の日本語で確認する。
- 介護DXの表現原則は「表現パターン選定」の判断材料に使う。
- **成果物:** 承認済みデザイントークン、共通部品一覧、タイポ表、余白表、テーマ規則、PC/SP仕様。ここで実装費用を確定する。

### フェーズC｜共通基盤の実装と全ページ接続

- 共通CSS／コンポーネント／テーマの管理元を構築し、サイトの**全ルート**から参照する。
- 独立HTMLにも同じ基盤の規格を適用する配信／ビルド方法を整える。
- 既存の色・文字・行間・枠・コンテナの重複指定を、影響範囲を検証しながら共通規格へ移行する。
- 作業はテーマ・機能単位で小さくコミットし、**個別ページを独立した改修案件として順番に完成させない**。
- ページ固有の図解・配置は、全体で承認された表現パターンと例外管理で扱う。
- **成果物:** 全サイト共通基盤、各ルートの適用記録、削除／残存CSS一覧。

### フェーズD｜全ページ一括の回帰・受け入れ確認

- 全公開ルート・全テーマ・主要状態を対象に、**PC／SPそれぞれブラウザ画像を取得**し、変更前後を比較。
- 共通部品は実寸で、全ルートはページ全体で評価。問題のある区画もURL別の応急CSSではなく、まず**共通部品・共通ルールの原因**を確認する。
- 改善が他ページを壊した場合は該当変更を戻し、原因と修正結果を記録する。
- **成果物:** 全ページ検証結果、実測数値、問題一覧、例外一覧、承認用PC/SPキャプチャ。

**フェーズA→B→C→Dは承認ゲート付き。** Aだけ、またはA＋Bだけ発注することも可能。**一括適用の品質保証ができないと判明した場合はCへ進まない。** これは「まずコンサルティング1ページを修正してから他ページへ展開」とは異なる方式である。

## 9. サイト全体の受け入れ基準（検証可能な定義）

### 9.1 数値・技術の合格条件

| 対象 | 合格条件 | 確認方法 |
|---|---|---|
| 文字ロール | 全ページで承認済みのフォント／サイズ／ウェイト／行間が適用 | Rendered Fonts・Computed Style・共通部品スナップショット |
| 文字色 | 本文・補足・背景が許容された組み合わせ | 実測コントラスト比＋画面確認 |
| 強制改行 | 意味不明な短行、配列spanの強制縦積みがない | DOM・CSS調査＋PC/SP目視 |
| 横はみ出し | 意図しないページ全体の横スクロールがない | `document.documentElement.scrollWidth <= clientWidth` 等の計測＋実際の操作確認 |
| 余白 | 共通コンテナの整列と役割別spacingが一致 | computed styleと全画面キャプチャ |
| 二重枠 | 意味のない重複枠・背景・影がない | 共通部品の承認済みデザインと目視照合 |
| 図解 | SPで文字が読め、図の意味が理解できる | 375／390pxでの実機・画面確認 |
| 操作 | CTA・ナビ・入力が全ページで使える | ブラウザ操作テスト |
| アクセシビリティ | キーボード、フォーカス、代替テキスト、色・モーション配慮 | 自動検査＋人の操作確認 |
| 回帰 | 全ページの意図した表現が維持されている | 変更前後のスクリーンショット差分と確認表 |

**注意:** `overflow-x:hidden` / `clip`で隠すだけの修正、ブラウザ表示を見ずにCSS値が合っているだけの修正、コンポーネントが作られただけの報告は**不合格**。一方、明示的に許可した**局所的な表の横スクロール**は例外として記録する。

### 9.2 デザインの合格条件

- 見出し→本文→図解の**視線の優先順位**が画面ごとに定まっている。
- 情報が異なるのに**すべて同じカード型**になっていない。
- 文章だけで理解しづらい部分に、内容に対応する図解・画面例・比較表が配置されている。
- 本文が狭く押し込まれ、右側に理由の説明できない空白を残していない。
- PCとSPの配置はどちらも承認済みの共通ルールに沿い、**内容の見え方は必要に応じて別設計**されている。
- サイト全体に統一感がありつつ、LP・業界・サービス固有の表現は残されている。

**「魅力的なサイト」は数値だけで自動判定できない。** デザイン品質の最終確認者（外注先のアートディレクター／クライアント）と承認手順を契約で明示する。
