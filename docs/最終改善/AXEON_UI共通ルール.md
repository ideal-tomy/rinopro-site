## 1. 目的と進め方

### 1.1 目的

公開サイト全体について、**文字組み・色・余白・コンテナ・枠・図解・レスポンシブ・検証**を一つの仕様で管理し、次を防ぐ。

- ページごとに品質・改行・余白がバラバラになる
- 1 ページ直すと別ページが崩れる
- CSS Modules / Tailwind / 独立 HTML が二重・三重に保守される

### 1.2 採用しない進行

- **URL 単位で「完成させてから次へ」**（例：コンサルだけ先に仕上げる）
- ページ固有の `*.module.css` を増やして場当たり修正する
- 独立 HTML を永続的に `public/` だけで手メンテする

### 1.3 採用する進行

1. **フェーズ A** — 全 URL・全スタイルの棚卸し（コード変更なし）
2. **フェーズ B** — 本書＋共通部品カンプの**承認**（コード変更なし）
3. **フェーズ C** — 共通基盤の実装と**全ルートへの接続**（テーマ・機能単位の小コミット）
4. **フェーズ D** — 全ページ横断の回帰・受け入れ

各フェーズは承認ゲートを挟む。A または A+B のみの発注も可。

### 1.4 「共通化」の意味

**全ページを同じカード・同じ行間・同じ構成にすることではない。**

- **意味が同じ UI 要素**（セクション見出し、標準本文、CTA など）は、**同じロール・同じ基準**で表示する。
- **内容の役割が違う区画**（比較、操作画面、長文、帳票サンプルなど）は、**承認済みの表現パターン**から選ぶ。
- ページの個性は **文言・図・写真・テーマ色・選んだパターンの組み合わせ**で残す。

### 1.5 フェーズ E / F（共通化完了のあと）

| フェーズ | 目的 | 成果物 |
|----------|------|--------|
| **E** | 基盤・横断の完了。全公開クラスタを ax シェルに接続し、部品契約と静的 LP（chuken）の Next 化まで行う | `phase-e-scope.md`、`component-contracts.md`、`url-registry` の ax 接続更新、`phase-f-backlog.md` |
| **F** | URL 単位の確認と調整（parity・改行・SP・カード微調整） | `acceptance-matrix` サインオフ、バックログ消化 |

- **E では** ページごとの原稿改行や旧 HTML ピクセル一致は行わない。
- **F の手順**は [`../ui-migration/phase-f-playbook.md`](../ui-migration/phase-f-playbook.md) に従う。
- 詳細スコープは [`../ui-migration/phase-e-scope.md`](../ui-migration/phase-e-scope.md)。

## 2. 適用範囲

| 区分 | 例 | 必ず共有 | 許容する差 |
|------|-----|----------|------------|
| 企業・案内 | トップ、about、問い合わせ | タイポロール、余白、コンテナ、コントラスト、検証幅 | Hero・写真・ブランド演出 |
| サービス | `/services/*` | 上記＋比較・工程・資料の**表現パターン** | サービス固有の図解・データ |
| 業界・記事 | `/industries/[slug]`、記事 | 本文・見出し・表・図の文字組み | 業界画像、記事の読み幅 |
| 静的 LP | `/lp/*`（現状 HTML 2 件） | 可読性・操作・余白・検証・**共通トークンへの接続** | **承認済みテーマ**（色・ディスプレイ書体） |
| デモ・体験 | `/demo/*`、`/experience/*`、見積導線 | 色の意味、階層、最小可読性、操作、端末適応 | 高密度 UI・状態表示 |

**例外は URL 名で増やさない。** `theme: corporate | care | …`、`density: standard | compact`、`diagram: responsive | scrollable` など**意味のあるバリエーション**で台帳に記録する。

実装前に **公開 URL 全件台帳**（動的ルート・非ナビ URL・HTML LP を含む）を作成する。項目例：`URL / 種別 / テーマ / スタイル由来 / 利用パターン / 検証 / 例外理由`。

## 3. 既にリポジトリで確定しているルール（実装時も遵守）

以下は `.cursor/rules/project-rules.mdc`、`text-contrast.mdc`、日本語折り返しルール、既存コードと整合する。**提案値より優先する。**

| ルール | 内容 |
|--------|------|
| 明背景の文字色 | 本文・見出しは濃色（`text-slate-900` 系、`text-text`、`--color-text-primary` 等）。**明背景に `text-white` 禁止** |
| `text-base` | **Tailwind の `text-base` は使わない**（`@theme` の `--color-base` と衝突し、ほぼ白文字になる） |
| 本文サイズ | **15px 未満を主たる説明文に使わない**（補足・UI ラベルは別ロール） |
| ガラス・半透明枠 | 明背景で輪郭が消える `bg-white/[0.06]`、`border-white/15` 等は使わない |
| 日本語見出し | `max-width: 14em` 等で artificial 改行しない。改行は **意味の切れ目**（`<br>` または行配列） |
| モーション | `prefers-reduced-motion` を考慮する |

### 3.1 既存デザイントークン（`src/app/globals.css`）

実装移行時は、まずこれらへ寄せ、新規 hex 直書きを増やさない。

| トークン | 値（概要） | 用途 |
|----------|------------|------|
| `--color-text` / `--color-text-primary` | `#1a1a1a` | 本文・見出しの基準 |
| `--color-text-sub` / `--color-text-secondary` | `#4a4a4a` | 補助（本文と混同しない） |
| `--color-accent-primary` | `#26418e` | ブランド青 |
| `--color-bg-base` / `--color-base` | `#fafaf8` | ページ地 |
| `--color-bg-neutral` | `#f4f4f2` | 交互背景 |
| `--color-border-light` | `#e5e5e0` | 区切り |
| `--line-height-body` | `1.5`（※下記移行対象） | 現行のグローバル既定 |

### 3.2 移行時に解消する既知の技術負債（本書の前提）

| 現状 | 共通ルール適用後の方針 |
|------|------------------------|
| `globals.css` で `p, li, …` に `line-height: … !important` | **役割別クラス**へ移し、要素一律の `!important` を廃止（依存調査後） |
| サービス系 CSS が `consulting-final` / `service-landing-shared` / `consulting-page` 等に分散 | **トークン＋表現パターンコンポーネント**へ集約。ページ名付き CSS は新規禁止 |
| `layout.tsx` の Noto Sans JP **400 のみ** | 700 等、ロール表で必要なウェイトを `next/font` で供給 |
| `public/lp/*.html` が独自 `<style>` | Next 上で**同じトークン・同じパターン**を使う再実装を目指す（二重保守しない） |
| コンテナ幅 1120 / 1140 / 1280 / 12.8% 混在 | **§5.2 の正式値**承認後に一本化 |

## 4. 文字（タイポグラフィ）

**§4.2 の数値は [提案・要承認]。** 承認前に画面と日本語原稿で検証する。UP Forward 実測は**役割分けの参考**であり、値の丸写しではない（詳細は [`UP_Forward_service_design_analysis.md`](./UP_Forward_service_design_analysis.md)）。

### 4.1 書体

| 役割 | 方針 |
|------|------|
| 日本語本文・一般見出し | **Noto Sans JP を標準系列として 1 本化**（`--font-noto-sans-jp` / システムフォールバック） |
| 英数字 UI | 原則本文系列。Geist は補助的に検証してから |
| 大きなディスプレイ見出し | 原則ゴシック。**テーマ `display-serif` は LP 等の承認テーマのみ**（kaigo の明朝はコピー対象ではない） |
| 短い英字ラベル（eyebrow） | 本文系列または承認済み mono |

### 4.2 タイポロール（PC / SP）

| ロール名 | PC（1280–1440） | SP（320–430） | 太さ | 使う場所 |
|----------|-----------------|---------------|------|----------|
| `display` | 48px / 1.30 | 32px / 1.35 | 700 | Hero 主コピーのみ |
| `page-title` | 40px / 1.40 | 30px / 1.40 | 700 | ページ主見出し |
| `section-title` | 34px / 1.45 | 26px / 1.45 | 700 | セクション見出し |
| `item-title` | 22px / 1.45 | 19px / 1.50 | 700 | 項目名・比較対象名 |
| `lead` | 18px / 1.75 | 16px / 1.75 | 400–500 | 要旨 |
| `body` | 16px / 1.75 | 16px / 1.70 | 400 | **標準本文（基準サイズ）** |
| `supporting` | 14px / 1.65 | 14px / 1.65 | 400–500 | 注釈・キャプション（主説明にしない） |
| `ui-label` | 13px / 1.45 | 13px / 1.45 | 600–700 | ボタン補助・フィールド名 |
| `eyebrow` | 12px / 1.40 | 12px / 1.40 | 700 | 短いラベル（重要説明にしない） |

- **見出しレベル（h1–h3）と見た目ロールは分離する。** アクセシビリティの構造を、デザイン都合で入れ替えない。
- デモ・帳票の高密度 UI は `data-dense` 等の**共通バリエーション**のみ。画面名だけの個別 px 禁止。

### 4.3 文字色（セマンティック）

| トークン | 提案値 | 既存との関係 |
|----------|--------|--------------|
| `text-heading` | `#111827` | `--color-text` と併存時は移行表で統一 |
| `text-body` | `#1F2937` | 薄灰本文禁止 |
| `text-supporting` | `#475569` | `--color-text-sub` と役割を揃える |
| `link` | `#1D4ED8` | 操作可能なリンク |
| `brand-primary` | `#26418E` | `--color-accent-primary` |
| `surface-page` | `#FAFAF8` | `--color-bg-base` |
| `surface-card` | `#FFFFFF` | |
| `border-subtle` | `#E5E5E0` | `--color-border-light` |

暗色背景・写真上・LP テーマは **背景と文字をセットで定義**。薄い文字色で「控えめ」にしない。

**コントラスト:** 通常文字 4.5:1 以上を目安（大きな文字は WCAG の大文字条件に応じ 3:1 以上）。色だけで意味を伝えない。

### 4.4 日本語の改行・行長

1. **1 段落は通常 1 つの連続テキスト。** 装飾目的で配列＋`span { display:block }` を積み重ねない。
2. 通常本文に装飾 `<br>` しない。段落分けは `<p>`。Hero 等、意図が明文化された例外のみ。
3. `keep-all` / `nowrap` を全文に一律適用しない。
4. 孤立 1〜2 文字行が出たら、**先にコンテナ幅・grid・min-width・フォント実寸**を点検。文言で誤魔化しない。
5. 長文は適切な行長（`ch`）を検討するが、**全本文を狭い固定幅にしない**。
6. 手動改行見出しは 320 / 375 / 390 / 430 / 768 / 1280 / 1440 で確認。PC と SP で改行一致は不要。
7. **機械判定のみで「自然な改行」を合格としない。** 目視キャプチャ必須。

### 4.5 読み物・長文（補足正本）

セクション型（宣言／読み物／一覧／工程／ハブ）、意味ブロック、コンテンツ構造化、全 URL 展開手順は [`AXEON_全サイト共通_テキスト表示ルール.md`](./AXEON_全サイト共通_テキスト表示ルール.md) を参照。§4.2 のロール数値と矛盾する場合は本書 §4 を優先し、補足正本を改訂する。

## 5. 余白・コンテナ

### 5.1 スペーシングロール [提案・要承認]

基準スケール：`4 / 8 / 12 / 16 / 24 / 32 / 48 / 64 / 80 / 96` px。  
**数値を全要素に均等適用しない。** 下表のロールで使う。

| ロール | PC | SP | 意味 |
|--------|----|----|------|
| `section-standard` | 上下 96px | 上下 64px | 通常セクション境界 |
| `section-compact` | 上下 64px | 上下 48px | 関連の強い連続区画 |
| `heading-to-lead` | 24px | 16px | 見出し→要旨 |
| `heading-to-content` | 40px | 28px | 見出し→主コンテンツ |
| `item-title-to-body` | 12px | 8–12px | 同一項目内 |
| `paragraph-to-paragraph` | 16px | 16px | 段落間 |
| `content-group` | 32–48px | 24–32px | 論点・図表のまとまり |

見出し・段落の margin は 0 リセット可。**距離は親の `gap` 等でロール別に付与**（UP Forward 実測の考え方と一致）。

### 5.2 コンテナ [提案・要承認]

| 名前 | 仕様 |
|------|------|
| `container-wide` | 最大 **1160px**、標準レイアウト・ヘッダー・図解 |
| `container-reading` | 長文用。`ch` 基準（カード内・比較内には強制しない） |
| ガター | PC 約 40px / タブレット約 32px / SP 約 20px |

- ヘッダー・本文・CTA の左右基準線を揃える。full-bleed 背景は可、**内側本文の基準位置は共通**。
- 親子で `max-width` と padding が二重にならないよう責務を分ける。
- Grid / Flex 子に `min-width: 0` 等、**横はみ出しの原因を構造で直す**。

## 6. 枠・カード・アイコン

- **意味のあるカード枠は原則 1 階層**（外枠＋内枠＋装飾枠の三重は禁止）。
- 小見出しと本文の並びだけなら **枠なしを先に検討**。
- 影・角丸・罫線は**共通部品のバリエーション**のみ。
- アイコンは識別・操作・状態用。**全項目に同じアイコン＝図解扱いにしない**。
- **視覚上の主役は 1 つ**を基本。

## 7. 表現パターン（コンテンツロール）

ページ非依存の部品として定義し、**必要なものだけ選ぶ**。全ページへの全挿入は禁止。  
kaigo LP（[`docs/demo-detail-lp-kaigo-pattern.md`](../demo-detail-lp-kaigo-pattern.md)）は **パターン選定の参考**。色・明朝・カード装飾のコピーはしない。

| パターン ID | 向く内容 | PC | SP |
|-------------|----------|----|----|
| `EditorialIntro` | 大見出し＋要旨 | 文字とビジュアルを役割配置 | 見出し優先、順序再設計 |
| `BeforeAfter` | 現状と改善後 | 比較できる配置 | 1 セットを切らず表示 |
| `ProcessFlow` | 工程・手順 | 関係が見える図 | 読めるステップ表示へ組替え |
| `DecisionComparison` | 選択肢と判断材料 | 表・軸・比較図 | 照合可能。必要なら局所横スクロール |
| `ProductScreen` | 操作・出力 | 画面主役、文は補足 | 読める範囲＋切替 |
| `Evidence` | 成果物・事例・数値 | 図版・実例主役 | 注釈・数値を小さくしすぎない |
| `Prose` | 長文・記事 | 可読幅 | 自然な段落 |
| `ContactCTA` | 問い合わせ | 明確なボタン＋短い補足 | タップ・余白優先 |

**セクション背景:** 隣接区画で背景を変え、スクロールのリズムを作る（kaigo の「生成り↔白↔濃色帯」の**考え方**。色そのものはテーマ依存）。

## 8. レスポンシブ・図解

1. PC / SP を**それぞれ完成画面**として設計（PC の縦積みだけは不可）。
2. 文章入り SVG の単純縮小禁止。必要なら HTML 化・図の簡略化。
3. 横スクロールは**表・タイムライン等、比較上必要な要素内のみ**。ページ全体の意図しない横スクロール禁止。
4. 図版はコンテナ内。縦横比・文字の読める寸法を共通仕様化。
5. SP 本文列の不自然な右余白を作らない。
6. タッチサイズ、フォーカス、`prefers-reduced-motion` を横断で統一。
7. ブレークポイントは**意味と担当コンポーネント**を台帳化。899 / 767 / 900 等の重複定義を整理。

**検証幅（必須）:** 320 / 375 / 390 / 430 / 768 / 1024 / 1280 / 1440（必要なら 1920）。Safari と Chrome の差を確認。

## 9. 実装・CSS 管理（フェーズ C の方針）

### 9.1 単一の管理元

| 層 | 管理内容 |
|----|----------|
| デザイントークン | 色、書体、サイズ／行間、余白、コンテナ、角丸、影、フォーカス |
| タイポロール | §4.2 のクラスまたはコンポーネント API |
| レイアウト | コンテナ、セクション、分割、比較、図版 |
| 部品 | ボタン、リンク、タグ、カード、入力、表、ナビ、CTA |
| テーマ | `corporate` / `care` 等。**URL 名での上書き禁止** |

新規ページは **config（セクション配列）＋既存パターン** で組み立てる。新規 `*.module.css` は原則禁止（例外は台帳＋理由＋検証）。

### 9.2 Tailwind・トークン

- 独自トークンは `--ax-*` 等、**`text-base` や `--color-base` と衝突しない接頭辞**。
- `src/lib/ui/service-reading-styles.ts` は移行期の参考。**正本は本書のロール表＋共通コンポーネント**へ統合。

### 9.3 静的 LP → Next

- `public/lp/kaigo-care-dx.html`、`chuken-enterprise-v2.html` は、承認後 **App Router + 同一トークン・パターン**で再実装。
- rewrite を HTML から Next へ切り替えるタイミングで、**旧 HTML は退避**し二重メンテを終える。

## 10. 受け入れ基準（フェーズ D）

### 10.1 技術

| 項目 | 合格条件 |
|------|----------|
| タイポロール | 承認済みサイズ／行間／ウェイト |
| 色 | 許容組み合わせ、コントラスト |
| 改行 | 配列 span の強制縦積み・意味不明短行なし |
| 横スクロール | 意図しないページ全体の overflow なし |
| 余白・コンテナ | 基準線・ロール spacing |
| 枠 | 無意味な二重枠なし |
| 図解 | SP で文字が読め、意味が通る |
| 操作 | CTA・ナビ・入力が使える |
| a11y | キーボード、フォーカス、代替テキスト、色・モーション |

`overflow-x: hidden` で隠すだけ、CSS 値だけ合っていて画面未確認、部品が置かれただけの報告は**不合格**。

### 10.2 デザイン（人の判断）

- 見出し → 本文 → 図の**視線順**が定まっている
- 内容が違うのに**同じカード型だけ**になっていない
- 文章だけでは足りない所に**適切なパターン**がある
- 統一感と**ページ固有の表現**が両立している

最終デザイン判断者と承認手順を契約で明示する。

## 11. 未承認・実装前に決めること

- §4.2・§5 の正式値（カンプと日本語原稿での確定）
- `--color-*` / Tailwind / CSS Modules → `--ax-*`（または統一トークン）の**対応表**
- Noto Sans JP のウェイトと `next/font` 設定
- 静的 LP のテーマ定義（care / chuken 等）と corporate の境界
- 共通 CSS を HTML 経由で配信しない場合の**ビルド・配信一本化**方式
- 公開 URL 完全一覧、認証画面の試験方法、例外承認者
- 品質の最終判断者、変更回数・予算・期限
