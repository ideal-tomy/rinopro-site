# 魅力的な Web サイト製作を実現するための学習内容

**作成日:** 2026-10-16  
**前提:** 本リポジトリの `/services/consulting` で起きたこと（[consulting-ui-text-readability-retrospective.md](./consulting-ui-text-readability-retrospective.md)）と、参考サイト UP Forward の実測（[UP_Forward_service_design_analysis.md](./UP_Forward_service_design_analysis.md)）を対比したメモ。  
**読み方:** 「諦める」前に、**何が足りなかったか**と**学ぶ順番**だけ押さえる。AI はこの順番の**代わり**にはならないが、**採寸・下書き・実装の手**にはなる。

---

## 1. 一言で言うと何が悪かったか

**デザインのセンス不足というより、「基礎の設計図がないまま、見た目の部品だけ差し替え続けた」ことが主因。**

- 良いサイトは **少数のルール**（文字の役割・余白・色・1画面の話の流れ）で全体が動いている。
- 当時のコンサル LP は **ルールがセクションごと・セッションごとに増え、矛盾した**（改行・14px 本文・ブレークポイント競合・階層の逆転）。
- AI は「それらしいカード UI」を出せるが、**ルール表と実機確認がないと、読みやすさには届かない**。

---

## 2. 良いサイト（参考）と、今のコンサル LP の違い

| 観点 | 良い B2B LP の例（UP Forward 実測のイメージ） | コンサル LP で起きていたこと |
|------|-----------------------------------------------|------------------------------|
| **タイポ** | 役割が少ない（見出し用・本文用・数字用など）。サイズは **数段**で固定（例: PC 見出し 36px / 本文 16–18px）。 | 12〜24px が混在。SP で **本文 14px**。同じカード内で **line-height 1.45 と 1.85** が共存。 |
| **階層** | 「誰の課題か」→「何をするか」が **大きさ・太さ・位置**で一目で分かる。 | 期間によって **お悩みより「検討」側の青太字が目立つ**逆転。 |
| **余白** | 見出しタグの margin は 0 でも、**ブロック単位の rhythm**（例: 32 / 40 / 64px）で揃える。 | 配列1要素＝`span`＋**`display: block`** で、**短い行の縦羅列**。2列比較の名残で **右の空白**。 |
| **色** | 背景・本文・アクセントが **3〜5色**に収まり、役割が固定。 | `#42516a` / `#334155` など **近い紺・グレー**が多く、ラベルと本文の区別が弱い。 |
| **レイアウト** | 1ストーリーで下に読む。装飾は **意味のある画像・大見出し**に寄せる。 | カード・矢印・薄青パネルなど **UI パターンの差し替え**が先に来た。 |
| **実装** | ブレークポイントが **はっきり**（例: 1350 / 540）。トークンで上書き。 | **899px と 767px** が重なり、同じクラスに別値が競合。 |
| **作り方** | 先に **採寸・タイポ表・余白表**、あと実装。 | 先に CSS とカード案。**合意した数値表がなかった**。 |
| **検証** | 決めた幅（例: 375 / 1440）で **毎回同じ URL** を見る。 | dev サーバー取り違えなどで **正しい画面を見ずに積み増し**。 |

**結論:** 参考サイトは「きれいなパーツ」ではなく **繰り返しのルール**で整って見える。こちらは **ルールがなく、パーツだけ増えた**状態だった。

## 3. AI だけでは洗練されない理由（学習の焦点）

| AI が得意 | AI だけでは足りない |
|-----------|---------------------|
| コードの下書き、一括リネーム、採寸スクリプト | **何を正とするか**（タイポ表・余白表）の決定 |
| 参考に「近い」コンポーネントの生成 | **ストーリーと階層**（誰の言葉が主役か） |
| バグ修正の提案 | **実機で同じ URL を見る習慬** |
| ドキュメント整理 | **1変更1テーマ**の判断とロールバック |

**学ぶべきは「プロンプトの巧みさ」より、上表の右列（設計・評価・検証）。** 2年かけなくても、**順番を間違えなければ**到達可能な範囲がはっきりしている。

---

## 4. まず何を学ぶか（推奨順・各段階のゴール）

### ステップ 1 — 読みやすさの最小セット（1〜2週間）

**学ぶこと**

- **タイポの役割**: ページ見出し / セクション見出し / リード / 本文 / ラベル の **5種類まで**に絞る。
- **サイズ**: BtoB では本文 **15px 以上**（本プロジェクト方針）。SP だけ 14px にしない。
- **行間**: 同じブロック内は **1系統**（例: 見出し 1.4〜1.5、本文 1.7〜1.85）。太字だけ 1.45 にしない。
- **コントラスト**: 明背景＋濃文字（プロジェクトルール）。`text-base` 文字色事故を理解する。

**ゴール:** 375px と 1280px で、**1枚の表**（px / weight / line-height / color）を書き、それ以外の値をコードに足さない。

**教材の方向:** 「Web タイポグラフィ basics」「UI の visual hierarchy」程度の短い記事・動画で足りる。デザインツールは後回しでよい。

---

### ステップ 2 — 日本語の折り返しとマークアップ（1週間）

**学ぶこと**

- **意味のない改行をデータに入れない**（`lp-japanese-wrap` / プロジェクトルール）。
- **配列1要素＝1行＋`display: block`** は、モバイルで「羅列」になりやすい → **1段落＝1要素**か、意図した `<br>` だけ。
- `word-break: keep-all` と **狭い列**の組み合わせで、1〜2文字落ちが出る理由。

**ゴール:** ご相談例のような長文を、**CSS 幅に任せて**読める。手動改行は最後の手段。

**参照:** [consulting-linebreak-layout-report.md](./consulting-linebreak-layout-report.md)

---

### ステップ 3 — レイアウトと余白（2〜3週間）

**学ぶこと**

- **余白は「要素の margin」より「セクションの padding / gap」**で揃える考え方（UP Forward はラッパー `margin-top` が型）。
- **8px グリッド**（4 / 8 / 16 / 24 / 32 / 48 / 64）の感覚。
- 2列比較は **行数が揃うときだけ**有効。揃わないなら縦積み。

**ゴール:** セクション間・見出し下・カード内を **3〜5個の spacing トークン**だけで表現できる。

**参照:** UP Forward 第14章（マージン・垂直リズム）

---

### ステップ 4 — 色と UI の抑制（1〜2週間）

**学ぶこと**

- **アクセント色は1つ**（＋ hover / 無効の派生）。本文・補足は **グレー2段**まで。
- 「きれいなカード」「影・角丸」は **情報が増えるとき**だけ。装飾先行は SaaS テンプレ感の原因。
- 参考サイトは **イラスト・大見出し・余白**で魅せるパターンが多い（UP Forward §1.4）。

**ゴール:** 新しい色や枠を足す前に「**この要素の役割は表のどれか**」と言える。

---

### ステップ 5 — CSS の土台（並行〜3週間）

**学ぶこと**

- **デザイントークン**（CSS 変数）と **1ファイルでの上書き順**。
- **ブレークポイントは2つまで**に減らす（例: 768 / 1200）。899 と 767 の二重定義を解消する考え方。
- DevTools の **Computed** で font-size / margin / 当たっている `@media` を読む。

**ゴール:** `consulting-page.module.css` のような「歴史的 SP 上書き」を、**トークン＋1メディアクエリ**に寄せられる。

**参照:** [consulting-typography-mobile-analysis.md](./consulting-typography-mobile-analysis.md)

---

### ステップ 6 — 制作プロセス（習慣・継続）

**学ぶこと**

- **参考は雰囲気ではなく採寸**（UP Forward のやり方 → 自サイトと並べる）。
- **受け入れ基準を1行で固定**（例: 「375px でお悩み h3 が 18px・本文 16px・14px なし」）。
- **1テーマ1コミット**（タイポだけ / 改行だけ）。
- **常に同じプロジェクトの dev URL** で見る（ポート取り違え防止）。

**ゴール:** AI に「この表と、この幅のスクショに合わせて」と渡せる。自分は **表の更新と OK/NG** だけ判断する。

---

## 5. 学習の優先度マトリクス（時間がないとき）

| 最優先（これだけで見た目が変わる） | 次 | 余裕があれば |
|-----------------------------------|-----|--------------|
| タイポ5役割＋本文15px以上 | 改行・羅列の構造修正 | 色の整理 |
| 1枚のタイポ表（375/768/1200） | 余白トークン（8px系） | モーション・微インタラクション |
| 実機確認のルーティン | ブレークポイント統合 | Figma 等のツール操作 |

---

## 6. コンサル LP に戻すときの最短チェックリスト

再開するなら、デザインを増やす前に **Yes が全部つくまで実装しない**。

- [ ] 375 / 768 / 1200 の **タイポ表**が1枚ある  
- [ ] SP 本文に **14px がない**（共有 CSS の 767px ルール含む）  
- [ ] ご相談例は **配列＋`display: block` 羅列**をやめた  
- [ ] **お悩み > 検討** のサイズ・色の階層が表と一致  
- [ ] ブレークポイントが **2系統に整理**されている  
- [ ] `npm run dev` は **rinopro-site** の画面だけを見ている  

---

## 7. まとめ

| 誤解 | 実際 |
|------|------|
| センスがないから2年かかっても無理 | **ルール未整備**のまま部品差し替えを続けたことが主因 |
| AI でプロ級は一発で作れる | AI は **表と採寸がないと**「それらしい」止まり |
| 全部学ばないと無理 | **ステップ1〜3**（タイポ・改行・余白）だけで、今回の不満の大半に効く |

**魅力的なサイト**は、天才のひらめきより **少数の決めたルールを、最後まで破らない**ことで近づく。参考サイトとの差は「パーツのセンス」より **そのルールの有無**だった。

次に手を動かすなら、新しいカードではなく **375px 用のタイポ表を1枚書く**ところからでよい。
