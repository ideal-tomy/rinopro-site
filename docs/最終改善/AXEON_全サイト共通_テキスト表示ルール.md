## 要約：どう作るのがベストか

### 推奨する3層（この順で揃える）

| 層 | 何を決める | 置き場・成果物 |
|----|------------|----------------|
| **1. ページ設計** | セクションの順序・読者の疑問・表示の型（A〜E） | ページごとの**構成表**（§2）。文言は触らない。 |
| **2. コンテンツ構造** | 段落・強調・引用・見出し行のデータ | `src/lib/content/*`（例: `homeLandingCopy.brandStory`, `ceo.message`） |
| **3. 表示** | ロール・余白・改行・暗背景 variant | `ax-role-*` + **少数の ax パターン** + ページ固有は `HOME_*` 等を**段階的に ax へ寄せる** |

**やらない方がよいこと**

- URL ごとに Tailwind を直書きで階層を再発明する
- 巨大な `AxReadingSection` 1つに全ページを押し込む
- `empathy.cards` など**別データへ差し替えるだけ**で本文を置き換える（意味・量の差分を必ず比較）
- 装飾（カード・太線・全段落リード）だけで済ませる

### 推奨する実装の型（リポジトリ現状に沿う）

```
lib/content/          … 構造化コピー（lines, emphasis, variant: quote）
        ↓
ui/ax/AxText          … eyebrow / section-title / lead / body 等
ui/ax/AxProse         … 段落のまとまり・gap
ui/ax/patterns/       … 既存 AxEditorialIntro。必要なら AxReadingBlock を追加
ページコンポーネント   … 型 A〜E を選び、パターンを組み合わせるだけ
```

- **短い導入（Hero・サービス頭）** → 既存 `AxEditorialIntro`（eyebrow + pageTitle + lead）
- **長い読み物（代表・名前の由来・about 長文）** → 構成表 B + **意味ブロック**（context → block lead → body）+ 限定 strong / quote
- **一覧・FAQ・工程** → 構成表 C / D + `item-title` + `body`、区切り線は細く
- **CTA** → 構成表 A。長い説明は**左揃え**を優先

トップの名前の由来・代表メッセージは、**層2・3の基準実装**として既に入っている（§9）。他 URL はここから**同じデータ形状とロール割当**をコピーする。

### 正本の関係（二重管理を避ける）

| 正本 | 役割 |
|------|------|
| [`AXEON_UI共通ルール.md`](./AXEON_UI共通ルール.md) | タイポロール数値・色・コンテナ・改行の共通原則 |
| **本書** | 長文サイト向けの**セクション型・読み物ブロック・展開手順・合格条件** |
| [`docs/ui-migration/component-contracts.md`](../ui-migration/component-contracts.md) | 部品ごとのレイアウト契約（追加時はここに1行） |
| [`docs/ui-migration/acceptance-matrix.md`](../ui-migration/acceptance-matrix.md) | URL 単位のサインオフ（本書 §12 の表はここへ統合してもよい） |

本書の SP 初期値は **UI 共通 §4.2 と矛盾したら §4.2 を直すか、本書を改訂**する。ページ専用 px の増殖は禁止。

## 1. 共通の考え方

### 1.1 読み手に三つの入口

1. **見出しだけ追う** → ページと各区画の話題が分かる  
2. **リードと強調だけ読む** → 主張が分かる  
3. **本文を読む** → 理由・条件・具体まで分かる  

すべてを強調すると入口がなくなる。短くする代わりに全文太字も禁止。

### 1.2 数値より先に関係を決める

セクション着手前にメモする（実装チケットの先頭でも可）。

- この区画で理解してほしいこと  
- **既存文案のうち**最初に読ませたい一文  
- それを支える説明・例・条件  
- 次の区画または CTA へのつながり  

その後にロールを割り当てる。**フォントサイズだけ先に変えない。**

### 1.3 長文は不具合ではない

- 4段落続く読み物は許容。全段落をリード化・箇条書き化は禁止。  
- 見出しやリードを本文から取り出したら、**同文を本文に重複しない**。  
- 段落分割・表示上の strong は可。**新しい要約文の創作**は別 PR・別提案。  
- 縦に長くなることは許容（読みやすさ優先）。

## 2. ページ全体を先に設計する

### 2.1 ページ構成表（テンプレ）

| 順番 | セクション | 読者の疑問 | 伝える要点 | 表示の型 | 次のつながり |
|------|------------|------------|------------|----------|--------------|
| 1 | 導入 | 何を相談できるか | 課題整理から支援 | **A 宣言** | 支援内容 |
| 2 | 支援内容 | 具体的に何をするか | 整理・比較・計画 | **C 一覧** | 自社に当てはめる |
| 3 | ご相談例 | 自分も対象か | 業務上の悩み | **D 比較** | 進め方 |
| 4 | 進め方 | どう進むか | 確認→計画 | **D 工程** | FAQ / CTA |
| 5 | FAQ・CTA | 相談してよいか | 条件・連絡 | **C + A** | 問い合わせ |

全ページに同じ順番は強制しない。**型の交互は目的ではない**（内容に合わせて選ぶ）。

### 2.2 見出しだけでストーリーが通るか

- ラベル「支援の内容」だけで終わらせず、**区画の結論を section-title に置く**  
- 導入・中盤・CTA で同じ説明が重複していないか  
- 次セクションに進む理由がなければ、装飾ではなく**並び・重複**を見直す

## 3. 文字の役割（ロールマップ）

### 3.1 基本ロール → 実装

| 表示の役割 | 用途 | 実装（優先順） | UI 共通 §4.2 相当 |
|------------|------|----------------|-------------------|
| 文脈ラベル | セクション種別・「英語で読めば」等 | `AxText role="eyebrow"` | eyebrow 12–13px |
| ページ見出し | ページ主題 | `page-title` / `AxEditorialIntro` | page-title |
| セクション見出し | 区画の結論 | `section-title` | section-title |
| ブロック見出し | 話題の切り替え（軸恩、項目名） | `item-title` | item-title |
| リード | 先に読ませる一文 | `lead` | lead |
| 本文 | 説明・理由・条件 | `body` / `AxProse` | body 16px / LH 1.7–1.75 |
| 補足 | 注記・キャプション | `supporting` | supporting |
| 本文内強調 | 残したい一句 | `body` + `strong` / semibold | サイズは body 同じ |
| 引用 | 発言・決意の引用 | `blockquote` パターン（左線は細く） | body 派生 |

### 3.2 読み物ブロック（意味のまとまり）

名前の由来で使っている **4段** を、暗背景・明背景共通の**構成パターン**として扱う。

| 段 | 例 | ロールの組み合わせ |
|----|-----|-------------------|
| Context | 英語で読めば、Axis On。 | **lead サイズ** + ブランド色（暗背景は薄青）。eyebrow サイズに落とさない場合は本書で「context-line」と呼び、**数値は lead / closing と揃える** |
| Block lead | 軸を持ち、前へ進む。 | `item-title` 相当 |
| Body | 説明段落 | `body`、LH 広め |
| Emphasis | 恩送りの一文 | body 内 semibold |

新規 `ax-role-context` は**不要**（lead + 色トークンで足りる）。トップだけ `HOME_BRAND_STORY_STYLES.meaningContext` に閉じている場合は、横展開時に `axeon-ui.css` の modifier へ寄せる。

### 3.3 ロール運用の注意

- 見出しレベル（h1–h3）と見た目ロールは分離（UI 共通と同じ）  
- 「28px と 16px に差がないから 32px に」は機械判断しない。幅・改行・余白を先に見る  
- リード・context・quote を全セクション必須にしない

## 4. セクションの型（A〜E）

### A. 宣言・CTA

見出し → 短い説明 → 行動。中央揃えは**短い見出しのみ**。2行以上の説明は左揃え優先。

### B. 読み物

文脈ラベル → 見出し →（署名）→ **意味ブロック** → 結び。本文は左揃え。カードは標準にしない。

### C. 項目一覧・FAQ

項目見出しと説明を近づけ、項目間を離す。区切り線は細く。FAQ は操作可能性（開閉）を示す。

### D. 比較・工程

図が主、テキストはキャプション + 必要なら lead。横スクロール時は続きが分かる UI。

### E. ハブ・一覧カード

タイトル + 違いが分かる一行〜短段落 + リンク。詳細ページの全文は載せない。

---

## 5. 行間と余白

UI 共通 §5.1 のスペーシングロールを使う。本書の意図だけ補足する。

| 関係 | 意図 |
|------|------|
| ラベル → 対応する見出し | 一組（`item-title-to-body` より狭く） |
| 見出し → リード・本文 | `heading-to-lead` / `heading-to-content` |
| 同話題の段落 | `paragraph-to-paragraph` |
| 話題の切り替え | `content-group`（24–40px 級） |
| セクション境界 | `section-standard` / `section-compact` |

- 親の `gap` と子 `margin` の二重取りに注意  
- `space-y-6` 一律だけで完了としない  
- 行間を広げてブロック間余白を代用しない  

---

## 6. 揃え・読み幅・カード

- SP 本文: ページガター（約 20px）を出発点。カード内 `p-6` とガターを重ねて狭くしない  
- SP 本文に不要な `max-width` を足さない  
- PC 長文: `ax-container-reading` / 40–44em を**読み物だけ**  
- 長文の中央揃え・薄灰本文は禁止（UI 共通 §3 と同じ）  

---

## 7. 日本語の改行

UI 共通 §4.4 + `.cursor/rules` の日本語折り返しに従う。

- **見出し・短いリード**: 意味の切れ目。`titleLines` 配列 or レスポンシブ `<br>`。`text-balance` だけで合格にしない  
- **本文**: `<p>` で話題分割。装飾 `<br>` しない  
- **「。」だけ孤立**: 幅・padding・フォントを先に点検。機械的に語句削除しない  
- **keep-all / nowrap**: 見出し全体への一括適用は避ける  

---

## 8. 色・強調・引用

- 明背景: 見出し濃色、本文 `#30343B` 程度。薄灰で階層を作らない  
- 暗背景: 白系 + context は薄青可。全段落を別色にしない  
- 強調: **話題あたりおおよそ1箇所**（ノルマではない）。サイズは body 同じ  
- 引用: 実際の引用のみ。代表メッセージの「」段落は quote パターン可  

---

## 9. 基準実装（リポジトリ内・2026-10-18）

| 内容 | コンテンツ | コンポーネント | スタイル |
|------|------------|----------------|----------|
| 名前の由来（夜景） | `homeLandingCopy.brandStory` | `HomeBrandStorySection.tsx` | `HOME_BRAND_STORY_STYLES` |
| 代表メッセージ | `homeLandingCopy.ceo`（`messageHeadingLines`, `message[]` + emphasis / quote） | `HomeCeoMessageSection.tsx` | `HOME_CEO_STYLES` |

横展開時は **同じデータ形状**（`emphasis`, `variant: 'quote'`, `headingLines`）を `lib/content` に寄せ、表示は ax パターンへ段階移行。

### 次の基準例候補（手順 §11）

| 型 | URL・セクション |
|----|-----------------|
| C 一覧 | `/services/consulting` 支援の内容 |
| D 工程 | 同ページ 進め方 |
| A CTA | 同ページ お問い合わせ帯 |
| B 読み物 | `/about` 長文 |

## 10. コンポーネントを増やすときの判断

| やる | やらない |
|------|----------|
| `AxReadingBlock`（context + blockLead + children）を **1ファイル**追加し、brandStory から利用 | 全ページを1コンポーネントに統合 |
| `component-contracts.md` に `ax.reading-block` を1節追加 | ページ名 `*.module.css` を新規作成 |
| 強調を `emphasis` 文字列で構造化（既存 ceo と同じ） | 全文自動 strong 置換 |

既存 [`AxEditorialIntro`](../../src/components/ui/ax/patterns/AxEditorialIntro.tsx) は **B の前半（eyebrow + title + lead）** まで。意味ブロックが複数ある読み物は Intro の下に ReadingBlock を並べる形がベスト。

## 11. サイト全体への適用手順

1. 対象 URL を [`acceptance-matrix.md`](../ui-migration/acceptance-matrix.md) と突き合わせ、**未整備セクション**に構成表と型 A〜E を付与  
2. `HOME_*` と `ax-role-*` の重複を洗い、同意味は ax に1本化  
3. 基準実装（§9）をサインオフ  
4. consulting の C / D / A を第2基準例として実装 → contracts 更新  
5. 同じ型のセクションを横展開（表で未反映を管理）  
6. 375 / 390 / 430 / 1280 目視。§12 合格条件  

**完了条件**: 例示した2セクションだけで終えない。型ごとに1基準例 + 全 URL 反映表。

## 12. 合格条件（チェックリスト）

- [ ] 見出しだけで主題と区画の関係が分かる  
- [ ] リード／強調と本文を見分けられる  
- [ ] 同話題は近く、別話題は離れている  
- [ ] 大見出しに句点だけ・1〜2文字孤立がない  
- [ ] 横はみ出し・過剰に狭い本文幅・長文中央揃え・薄文字がない  
- [ ] 区切り線・STEP 番号が本文より目立ちすぎない  
- [ ] 原文の主張・条件が欠けていない（重複抽出もない）  
- [ ] 段落数だけで不合格にしない  

確認幅: **375 / 390 / 430 / 1280**（UI 共通 §10 と同じ）。記録は acceptance-matrix へ。
