# AXEON 半内製化ページ 改修指示書 v1

## 依頼

既存の「半内製化」ページを、以下の構成・掲載内容に改修してください。

目的は、長く重複している説明を整理し、「課題の整理から開発・運用まで継続して支援し、社内で対応できる範囲を広げるサービス」であることを、図解と短い文章で伝えることです。

コンサルティングページと、ヒーロー・見出し・ページ内リンク・問い合わせ導線のUIを統一します。ただし、すべてのセクションを同じカード形式にする必要はありません。

今回の指示書が、以前の半内製化ページに関する構成指示より優先します。削除対象を復活させないでください。

## 1. サービスの理解：実装前に共有する前提

半内製化は、コンサルティングと開発を継続して提供する契約を想定しています。

- 社内メンバーと業務の課題を確認する。
- 開発が必要なものと、業務手順の変更等で対応するものを整理する。
- 必要なシステムの開発・導入・運用を支援する。
- 別の開発会社が関わる場合は、打ち合わせに同席し、要件や進め方の確認を支援する。
- 実案件を通じて知識と手順を共有し、社内で対応できる範囲を広げる。

「自社ですべて開発する」「最後は必ず外部支援が不要になる」ことを約束するサービスではありません。社内と外部の分担を決め、専門的な部分は外部支援を続けられる説明にしてください。

コンサルティングページは「何を変え、どこから取り組むかを検討する計画」が中心です。半内製化は、その検討をしながら実行・運用まで支援することが中心です。開発工程に課題整理や要件検討が含まれていることは問題ありません。

## 2. 作業対象と進め方

- リポジトリ内で現在の半内製化ページのルート・ファイルを確認してください。URL名やファイル名を推測して新規ページを作らず、既存ページを改修します。
- 最初に、既存のコンサルティングページの実装、共通ヘッダー・フッター、画像、開発タブ、問い合わせ先を確認します。
- コンサルティングページの最新UIを実装上の基準にします。古いスクリーンショットや古い構成より、承認済みの最新実装を優先してください。
- 既存のフレームワーク、フォント、アイコン、共通コンポーネントを使ってください。
- 他ページの掲載内容を変更しないでください。必要な共通部品の変更は、他ページへの影響を確認します。
- 新規パッケージや新しい作業ルールファイルの追加を前提にしません。
- 実装・必要なビルド・ブラウザ確認まで行います。本番公開は今回の依頼に含みません。

## 6. ヒーロー

### 配置

- 淡青の背景に、PCは左文章・右画像。コンサルティングと同じ比率・余白を使います。
- SPは文章→画像の縦並び。
- 現在の中央寄せ・文章だけのヒーローは置き換えます。

### 掲載文

H1：

> 半内製化

太い説明：

> 課題の整理から開発・運用まで、社内メンバーと一緒に進めます。

通常の説明：

> 必要な仕組みを作りながら、知識と手順を共有し、社内で運用・改善できる範囲を広げます。

現在掲載されている「月額の支援・3か月ごとの更新」という契約条件は、既存の正式な条件であることを確認し、短い補足として保持してください。料金や無料相談の条件を新しく作らないでください。

### 右側画像

- 現在「開発の進め方」の冒頭にある、AXEONの5工程の支援範囲画像を移動します。
- ③システム開発、④導入・展開、⑤運用・保守を囲むオレンジ枠を含め、現在の表示を維持します。
- 元画像の①②、下部の紺色AXEON帯も残し、全体を表示します。
- 枠が画像に含まれている場合は追加しません。CSSで重ねている場合は画像基準の比率で位置を保持します。
- 画像を切り抜かず、比率を維持し、`object-fit: contain`。
- 追加の外枠・背景カード・強い影は不要です。
- 開発タブ内でこの画像を重複表示しないでください。画像直下の「③〜⑤が主範囲」のキャプションも、必要ならヒーロー画像の下に一度だけ移します。
- **各開発工程に置かれているイラストは移動・削除しません。移動対象は冒頭の5工程画像だけです。**

## 8. 支援の進め方：2つの既存セクションを統合

### 表現する関係

この図が示すのは、社内とAXEONの関わり方・引き継ぎの進み方です。後半の開発工程と同じ「現状整理→要件化→試作→本実装」を繰り返さないでください。

H2：

> 支援の進め方

短い導入：

> 実際の業務を一緒に進めながら、社内で対応できる範囲を広げます。

| 段階 | タイトル | 説明 |
| --- | --- | --- |
| 1 | 課題と担当を整理する | 業務の課題を確認し、社内と外部で担当する範囲を決めます。 |
| 2 | 小さく開発して確かめる | 社内メンバーと試作を確認し、必要な機能や手順を具体化します。 |
| 3 | 運用しながら引き継ぐ | 実際に使いながら、操作・管理・変更の手順を共有します。 |
| 4 | 社内で改善できる範囲を広げる | 社内で対応する業務を増やし、専門的な部分は外部が支援します。 |

図の下に一度だけ掲載：

> 必要に応じて、開発会社との打ち合わせにも同席し、要件や進め方の確認を支援します。

### デザイン

- 添付参考画像4枚目の「段階ごとに少し上がっていく4つのパネル」の配置を参考にします。
- 参考画像の会社名・サービス名・文言・ボタンはコピーしません。
- PCは幅広コンテナに4項目を横並び。上端を少しずつ上げ、段階的に進むことが伝わる図にします。
- 大きな段差や過剰な空白は作らず、段差は各12〜16px程度を初期値とします。
- 各パネルはタイトルと短い説明を主役にします。文字が読みやすい余白を確保します。
- 段階表示は小さい「1〜4」だけにし、01・STEP 01・英語ラベルを重ねません。
- 最終段階を濃紺またはブランドブルーで強調します。3段階目をAIの特別サービスとして強調する参考画像の構造は持ち込みません。
- 「完全内製化」「自律運用を保証」等の表現を追加しません。
- 旧図の診断1〜2週間・実装1〜2か月を、保証された期間として新図に転記しません。必要な期間は案件ごとの検討事項です。
- この図をページ全体の中心となる見せ場にします。

SPでは4項目を縦に並べ、細い接続線などで連続性を示します。PCの段差は解除します。横幅を縮小して4列を維持せず、説明をホバーや反転に隠さないでください。

## 9. 支援を始める前に確認すること：ステップではなく一覧

H2：

> 支援を始める前に確認すること

説明：

> 現在の体制や業務に合わせて、担当する範囲と進め方を確認します。

| 表示する項目名 | 説明 | アイコンの例 |
| --- | --- | --- |
| 社内で担当する範囲 | どこまで自社で対応し、どこを外部に任せるかを確認します。 | 分担・範囲 |
| 担当者と使える時間 | 誰が参加し、どの程度の時間を確保できるかを確認します。 | 人・時計 |
| 知識と手順の共有 | 何を覚え、どんな手順を残す必要があるかを確認します。 | 書類・本 |
| 開発・運用の環境 | 現在のツールや権限を、どこまで利用できるかを確認します。 | 設定・ツール |
| 開発会社との分担 | 誰が要件を伝え、確認し、契約や管理を担当するかを確認します。 | 対話・連携 |

### デザイン

- 添付参考画像5枚目（PC）と6枚目（SP）の、アイコンと短い名称が目につく一覧表示を参考にします。
- 参考画像の「仕様書」「FAQ」等の掲載内容は使いません。上記5項目を表示します。
- 5項目は並行して確認する事項です。番号や矢印は付けず、工程図にはしません。
- PCは5項目を横並び。淡い背景、青い線画アイコン、濃紺の太い項目名で構成します。
- 長い段落のカードに戻さず、アイコンと項目名を最初に認識できるようにします。
- 説明は各項目を選択すると下の共通説明欄に表示する方式を基本とします。初期状態でも1項目の説明が読める状態にします。
- 選択項目は枠・下線・背景などでも区別し、色だけに依存させません。選択によりレイアウトが大きく跳ねないようにします。
- SPは原則2列。5番目は同じ幅で配置し、埋め合わせの6番目を作りません。参考画像の3列を使うために文字を小さくする必要はありません。
- 項目はボタンとして操作でき、キーボード・フォーカス表示・選択状態を整えます。説明欄と関連付けます。
- 添付7枚目の8段階ステップ表現は、ここには採用しません。

## 10. 自社で進める際の課題と支援：対比を明確にする

H2：

> 自社で進める際の課題と支援

現在の左右対比を活かし、同じ行で課題と支援の対応が分かるようにします。

| 自社で進める際の課題 | AXEONの支援 |
| --- | --- |
| 何を開発すべきか決めにくい | 業務を確認し、開発するものと手順変更で対応するものを整理します。 |
| 開発会社への説明・確認が難しい | 要件整理、打ち合わせへの同席、提案内容の確認を支援します。 |
| 担当者に知識が集中する | 実案件を通じて知識を共有し、操作・管理の手順を整えます。 |

### デザイン

- PCは左に課題、右に支援。各列の見出しを明確にします。
- 左は淡い暖色または中立色、右は淡い青。左に暖色、右に青の縦アクセントを入れます。
- 3つの対応を行単位でそろえ、課題の隣に対応する支援が見えるようにします。
- タイトルと要点は十分な大きさ・太さにします。細かい箇条書きだけの2枚のカードに戻さないでください。
- 派手な赤の警告表示や煽るコピーは使いません。
- SPは「課題1→支援1」「課題2→支援2」「課題3→支援3」の順に並べます。課題3つの後に支援3つを並べると対応が分かりにくくなるため避けます。

## 13. 文章・アクセシビリティ

- この指示書の文言を基本にします。抽象的な営業コピーへ書き換えません。
- 「一気通貫」「道筋」「次の一手」「仕様の自然増殖」「判断と改善の型を移す」など、意味が伝わりにくい言い回しを追加しません。
- 「確認する」「整理する」「比較する」「共有する」などの具体的な行動で説明します。
- IT用語は必要な箇所だけに使います。既存の開発工程は今回の対象範囲を超えて全面リライトしません。
- 図解の文字は原則HTMLで保持し、接続線やアイコンをCSS/SVGで描きます。ページを1枚の画像にして実装しません。
- 重要な説明をホバーだけに隠しません。
- 既存タブ・新しい確認項目の操作・問い合わせリンクに、十分なタップ領域とフォーカス表示を用意します。
- 新たに表示アニメーションを付ける場合は既存サイトの方式を使い、`prefers-reduced-motion` に対応します。アニメーション失敗で文字が消えたままにならないようにします。

## 14. 確認と完了条件

既存プロジェクトに必要なビルド・型チェック等を行い、実ブラウザで各セクションを確認してください。確認できなかったものは、そのまま未確認として報告します。
