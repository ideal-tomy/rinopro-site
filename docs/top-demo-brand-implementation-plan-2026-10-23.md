## 1. 目的と完成条件

AXEONから開いた建設デモは、画面を移動しても、概算見積もり・問い合わせまでAXEONとしてつながる。IDEALから開いた場合はIDEALとしてつながる。

トップ掲載の4件について、紹介内容と遷移先が一致し、入口から体験終了までに別ブランドへの意図しない誘導がないことを確認する。

外部の共通デモを引き続き利用する。アドレスは `construction-demo-six.vercel.app` などのままで、表示ブランドと各出口を流入ブランドに対応させる。AXEONドメイン内への移設・プロキシ化・ドメイン統合は対象外。

完成条件:

- AXEON入口 → 建設ハブ → 写真整理 → 報告・提出 → 現場オペ → ハブの移動でブランドを維持する。
- ハブと完了画面の見積もりCTAが、同じブランドの見積もりを別タブで開く。
- 見積もりの入力・閉じる・再開・再読み込み・共有URLでもブランドを維持する。
- 建設ハブの「相談する」は流入ブランドに対応する問い合わせ先になる。
- ロゴ・ヘッダー・フッター・「サイトに戻る」・完了画面に既存の外部リンクがある場合も、解決済みブランドと整合する。
- 本番で必要な見積もりCTAが実際に表示され、操作できる。必要なCTAの非表示は未解決とする。
- IDEALの既存URLと、既存のデモ機能・画面遷移を壊さない。
- トップの残り3件も、紹介内容・実リンク・終了時の導線まで確認する。

## 3. ブランドとURLの仕様

### 3.1 受け取りと既定値

- 有効なブランドは `axeon` / `ideal` の2種類。
- 建設デモでは、URLの有効な `brand` を最優先する。
- 未指定・不正値の場合は、既存導線との互換性のため `ideal` として解決する。
- 解決したブランドは以後のリンクに明示する。localStorage、セッション、参照元ヘッダーに依存しない。
- 複数タブでAXEON版とIDEAL版を同時に使っても混ざらない。
- 見積もりアプリ全体の既定値は変更しない。見積もり側は自分の既存仕様でブランドを解決し、その解決値をURLに保持する。

### 3.2 パラメータの役割

| パラメータ | 用途 | 方針 |
| --- | --- | --- |
| `brand` | ブランド選択 | 対応する各遷移で明示・維持 |
| `from=photo` / `from=report` | 建設デモ内の画面連携 | 現状の動作を維持。流入元の用途で上書きしない |
| `from=construction-demo` | 見積もり側のデモ識別 | 現状を維持 |
| `kit` / `industry` / `cat` | 見積もりの初期設定 | `report-auto` / `construction` / `internal` を維持 |
| `return` | 戻り先 | 今回は新設不要。既存の検証仕様を迂回しない |

実装後の例:

```text
AXEONトップ → https://construction-demo-six.vercel.app/?brand=axeon
ハブ → /photo?brand=axeon
写真 → /report?from=photo&brand=axeon
報告 → /ops?from=report&brand=axeon
ハブへ戻る → /?brand=axeon
見積もり → {ROI_ORIGIN}/?kit=report-auto&industry=construction&cat=internal&from=construction-demo&brand=axeon
```

URL生成は `URL` / `URLSearchParams` で行い、必要な既存クエリ・ハッシュを保つ。内部遷移ヘルパーに任意の外部URLを渡さない。外部の問い合わせ先はブランド別の設定から選ぶ。

## 4. 作業手順

### Phase 0: 実装前の確認

1. 各リポジトリの差分と公開URLを確認し、既存変更を保護する。
2. 公開環境で建設の体験完了まで進み、ユーザーが見た実際の見積もりリンクを採取する。初回調査では完了後の実リンクは未取得。
3. `NEXT_PUBLIC_ROI_SIMULATOR_URL` の公開環境での有無、クライアントへの受け渡し方法を確認する。公開JSに未置換の参照が残った理由はこの段階で確定する。秘密値や環境変数一覧を記録しない。
4. AXEONの正規問い合わせURLを、サイト設定・公開ドメインと照合する。候補は `https://axeon.jp/contact`。コードに確定値として入れる前に、フォームの到達性とクエリ受け取りを確認する。
5. 製造の実画面を確認し、「現行リンク先を維持して紹介を変更する案」と「紹介に合うデモへリンクを変更する案」を別途提示する。ブランド導線の技術修正だけを理由に、どちらを掲載するかは決めない。

### Phase 1: 建設デモの共通処理

`construction_demo/lib/demo-brand.ts`（新規案）に次を集約する。

- `DemoBrand` 型とブランド値の正規化。
- ブランド別の問い合わせ先設定。
- 既存クエリを保って `brand` を付ける内部URL生成処理。

`lib/roiLink.ts` はブランドまたは解決済み設定を引数で受け取り、`brand: "ideal"` の固定を外す。`lib/hub.ts` の単一 `CONTACT_URL` はブランド別の取得処理へ置き換える。

サーバーとクライアントの両方から同じURL生成処理を利用できるようにし、共通処理内で `window` やサーバー専用APIを参照しない。

ROIオリジンはサーバーで解決し、クライアントで表示する完了CTAへシリアライズ可能な設定として渡す構成を第一候補にする。現在の環境変数参照がクライアントに未置換のまま残る場合も、この構成で解消する。環境変数が未設定ならCTAを非表示にする既存仕様を維持する。

### Phase 2: 建設の各画面へ接続

| 対象ファイル | 修正内容 |
| --- | --- |
| `app/page.tsx` | `searchParams` からブランドを解決し、ハブへ渡す。既存 `embed=intro` の分岐と `view` の動作を維持 |
| `components/HubView.tsx` | 各カード・見積もり・相談先を同じ解決済みブランドから生成 |
| `app/photo/page.tsx` / `components/PhotoSortDemo.tsx` | 写真画面へのブランド受け渡し、ハブ戻りと `/report?from=photo` にブランドを保持 |
| `app/report/page.tsx` | ブランドとROI設定を受け取る構成に調整。ハブ戻りと `router.push("/ops?from=report")` にブランドを保持 |
| `components/WorkflowActions.tsx` | 完了時に表示する見積もりCTAへ設定を渡す。複数の表示箇所を全て対象にする |
| `components/RoiPaybackCta.tsx` | 解決済みの見積もりURLを使用。別タブ・`noopener noreferrer` を維持 |
| `app/ops/page.tsx` / `components/ops/OpsApp.tsx` / `components/ops/OpsShell.tsx` | ブランドの受け渡しとハブ戻りに対応。既存の `from=report` の判定を維持 |

報告画面などが既存のClient Componentである場合、ページをサーバーの薄い入口と既存UIのClient Componentに分ける方法を優先検討する。UIの一括書き換えは避ける。採用する構成は対象Next.jsのガイドと照合する。

`KANRI_OPS_URL` は補助アプリがブランドクエリを解釈することを未確認のため、機械的に `brand` を追加しない。ログイン画面・試用可能な経路の外部導線を確認し、別ブランドへの誘導があれば追加対象として記録する。

### Phase 3: 見積もりアプリのブランド保持

追加確認で `roi-simulator/src/lib/url.ts` の `buildParams()` は、現在 `brand !== 'axeon'` の場合だけブランドを出力していることが判明した。

そのためAXEONのURLが更新されると `brand` が消える。公開環境がIDEAL既定の場合、再読み込み時にIDEALに変わる可能性がある。現時点でその環境条件による公開再現は未確認だが、URLの保存仕様として修正する。

- `buildParams()` は、解決済みブランドが渡されたらAXEONも明示して出力する。
- `App.tsx` からURL書き戻し・共有に、解決済みのブランドが渡ることを確認する。
- `kit` を閉じる操作では、既存仕様どおり `kit` と回答を外し、`brand`・`from`・業界・カテゴリを維持する。
- `src/lib/brand.ts` の既定値やIDEAL向け文言は変更しない。
- `SiteContextBar.tsx` のIDEAL専用条件はブランド保持だけを理由に変更しない。ただし、実際に表示されるロゴ・ヘッダー・フッター・戻り導線・完了画面の外部リンクは全て点検し、別ブランドへ誘導する既存リンクがあれば修正する。存在しないAXEON用の新規「サイトに戻る」UIは別要件とする。
- URLからの状態復元、共有URL、埋め込みURLの生成でも、明示されたブランドを維持する。異なるブランドの保存状態を復元する機能がある場合、回答等の復元で現在のURLから解決したブランドを上書きしない。

現行の `roi-simulator/src` では `localStorage` / `sessionStorage` を使う保存処理は検索上見当たらず、`lib/url.ts` にURLの読み取り・書き戻し・共有・埋め込みURL生成がある。保存データによる上書き不具合が確認済みとは扱わない。実装時に他の保存経路の有無を再確認し、存在する機能を検証する。今回のために保存機能を新設しない。

### Phase 4: 掲載元のURLを修正

`rinopro-site`:

- `src/lib/content/top-featured-demos.ts` の建設URLを `/?brand=axeon` にする。
- `src/lib/content/industry-lp/external-demos.ts` の建設・報告書URLにも `brand=axeon` を付ける。
- 同じ建設ドメインをリポジトリ全体で検索し、実際に使われる他の入口があれば更新する。過去の報告書や参照資料は実リンクと区別する。
- 同じURLの定義が複数ある場合は共有定数に寄せ、トップと業界LPのずれを防ぐ。
- `manufacturingIdeal` は内容を表さないため、実デモに沿った定数名へ変更し、参照を更新する。

IDEAL側:

- 稼働するIDEALサイトのリポジトリと掲載箇所を特定し、建設・報告書の入口を `brand=ideal` にする。
- パラメータなしでも従来どおりIDEALとして動くため、既存リンクは移行中も利用できる。

製造・図面承認・保育は現状ブランド分岐を必要とする外部導線が確認されていない。入口だけに無効な `brand` パラメータを追加して対応済みとは扱わない。

### Phase 5: 製造の紹介内容と他デモの確認

製造の紹介内容の選択は、ブランド導線修正から分けて提示する。未決定の間もP0のブランド修正は進められるが、製造の内容不一致は解決済みと扱わない。

| 案 | 修正内容 | 判断材料 |
| --- | --- | --- |
| A: 現行リンク先を維持 | 品質不具合対応コンソールに紹介文とトップの画面表現を合わせる | このデモをトップで紹介したいか |
| B: 現行の紹介テーマを維持 | ナレッジ回答・出典提示を体験できるデモへリンクを変更する | 候補デモの実機能・公開状態・ブランド導線が紹介に合うか |

掲載内容の方針が決まってから、該当案の差分を作成する。

- `top-featured-demos.ts` のタイトル・リード・Before/After・タグを実際の操作に合わせる。
- `TopFeaturedDemoShowcase.tsx` の製造用表示と関連サンプルを確認し、「質問→回答・出典」の表現が残る場合は合わせて変更する。
- URLの変更だけで完了にせず、トップで示す結果を実デモで体験できることを確認する。

製造・図面承認・保育は主要操作を終了まで実行し、ヘッダー・フッター・結果画面・モーダル・新規タブのリンク先を確認する。条件付きのAXEONデモ選定ページへの戻り導線は、入口条件を含めて確認する。問題がなければデモ本体の変更は不要。

## 5. 検証計画

| ケース | 合格条件 |
| --- | --- |
| AXEONのトップと建設LPから開始 | `brand=axeon` が付き、相談先もAXEON |
| IDEALの入口から開始 | `brand=ideal` が付き、相談先もIDEAL |
| 建設URLにブランドなし・不正値 | 従来互換のIDEAL。生成されるリンクには解決済みブランドを明示 |
| `/photo` `/report` `/ops` へ直アクセス | 指定ブランドを認識し、ハブへ戻っても維持 |
| 写真→報告→管理 | `from=photo` / `from=report` による従来の連携動作とブランドを両立 |
| 報告の完了CTAを各表示箇所から開く | 同一ブランド・正しいkitの見積もりが別タブで開く |
| 見積もり入力→閉じる→再開→再読み込み | ブランドが変わらず、閉じた後に業界を選べる |
| AXEONの共有URLをIDEAL既定環境で開く | AXEONを維持。通常のURL書き戻し後も明示値が残る |
| AXEON版とIDEAL版を同時に開く | タブ間でブランドが混ざらない |
| ROIオリジン未設定の互換性テスト | CTA非表示で主要操作は利用可能。ただし本番の見積もり導線の合格条件とは分ける |
| 本番で必要な見積もりCTA | 表示され、正しいブランド・設定の見積もりを開ける。非表示なら未解決として報告 |
| ロゴ・ヘッダー・フッター・戻り・完了画面 | 表示される全外部リンクの実URLが解決済みブランドと整合する |
| URLからの復元・共有・埋め込み | 明示したブランドを維持。共有・埋め込みURLにもブランドを保持 |
| 保存データの復元機能が存在する場合 | 別ブランドの保存データを復元しても、現在のURLの明示ブランドを上書きしない。機能がなければ該当なしと記録 |
| 埋め込み・スマートフォン | 既存の埋め込み表示と完了CTA・戻る操作が使える |
| トップの4件 | 紹介内容・リンク先・終了時の外部導線が一致 |

小さい自動テストは、ブランド正規化・クエリの保持・見積もりURLの往復に絞る。特にAXEONを省略しないURL保存と、既存 `from` を壊さない条件を回帰テストにする。既存ツールを優先し、この作業だけのためにテスト依存を追加しない。

各変更リポジトリで利用可能な型チェック・ビルドを実行する。実行前に `package.json` とフレームワークのバージョンを確認し、使えない既存lintコマンドをそのまま合格判定に用いない。複数TSXを編集した場合はReactの関連スキルに従ってレビューする。

ブラウザで最終リンクを取得し、表示ブランドと実際の `href` を両方記録する。ブラウザの実行手段がない場合は未確認を明記し、HTTP 200だけで完了としない。

## 6. 公開順序と切り戻し

1. ローカル・プレビューで建設デモと見積もりアプリを双方検証する。
2. 見積もりアプリのURL保持修正を先に公開する。
3. 建設デモのブランド対応を公開し、既存IDEAL入口とAXEON指定入口を確認する。
4. AXEON側・IDEAL側の掲載URLを更新・公開する。製造紹介の変更は掲載方針が決まった別差分として扱う。
5. 公開中の実際のAXEON・IDEAL双方の入口から操作し、完了・見積もりまで再確認する。各画面の表示ブランドと全出口の実URLを記録する。必要な見積もりCTAが非表示なら未解決として残す。

公開は本PLANの作成では実施しない。実装時の依頼範囲に応じて進め、公開が未承認の場合はレビュー可能な差分と検証結果を揃えてから承認を求める。依存関係やOSソフトウェアの追加・変更が必要になった場合も、対象と影響を示して実行前に確認する。

環境変数の変更が必要な場合は対象プロジェクト・環境・再ビルドの要否を明記する。変数追加だけで既存配信JSが更新されるとは扱わない。

切り戻しは今回の変更に限定したrevert／直前デプロイへの復帰で行う。共有ブランド対応を戻す場合は、先に掲載元の新しい入口を戻す。履歴の書き換え・強制push・既存作業のリセットは行わない。

- AXEON／IDEAL別の入口・内部遷移・見積もり・問い合わせURL一覧。
- 型チェック・ビルド・回帰テスト・ブラウザ検証の結果。
