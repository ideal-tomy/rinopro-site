# AXEON Webサイト UI・UX改善指示

## 作業目的

AXEONの既存トップページについて、スマートフォンでの日本語の改行と、意図の分からない余白・配置を改善してください。PCで成立している表示は保ちながら、スマートフォンで読みやすく操作しやすい状態にしてください。

対象リポジトリ： https://github.com/ideal-tomy/rinopro-site

今回は既存サイトの改善です。以下の範囲を調査し、必要な修正と表示確認まで進めてください。

## 1. 最初に現在の状態を確認する

- 現在のブランチ、作業中の変更、プロジェクトの起動・検証方法を確認する。
- ユーザーの未コミット変更を上書きしない。
- 実際のコードと画面から原因を確認する。過去の説明やファイル名を、現在の事実とみなさない。
- 読めないコード、使えない画像、起動できない画面がある場合は、その制約を明記する。

次のファイルは調査候補です。存在と現在の内容を確認してください。

- `src/app/globals.css`
- `src/components/home/HeroSection.tsx`
- `src/components/home/HomeEmpathyCards.tsx`
- `src/components/home/HomeValuesSection.tsx`
- `src/components/home/HomeClosingCta.tsx`
- `HomeLandingSectionHeading.tsx` に相当する共通見出し
- トップページのコンテナ、文字、余白を決めている関連部品

見た目の問題について、対象要素、原因となる指定、影響する画面幅、修正方法を短い表で示してから作業を進めてください。

## 2. 今回の変更範囲

対象はトップページと、その表示を修正するために必要な共通CSS・部品です。

優先順位は以下の順とします。

1. スマートフォンの見出しの不自然な改行と、句読点の孤立。
2. 長文の読みにくさと、使える幅を狭めている余白。
3. 非表示要素や幅制限によって残る、意味のない空き領域。
4. 見出し、画像・デモ画面、CTA、補足の配置と視覚的な優先順位。

文章の内容、画像、リンク先、既存機能を維持してください。新しいセクション、装飾、ライブラリは追加しません。リポジトリ全体の共通化やデザイン刷新も今回の対象には含めません。

共通部品の変更が下層ページにも影響する場合は、その影響を確認してください。可能ならトップページに限定した指定で対応します。

## 3. 日本語の表示ルール

### 本文

- 長い本文はスマートフォンで原則左揃えにする。
- ブラウザの自然な折り返しと禁則処理を基本にする。
- 端末幅に合わせた本文の強制改行を追加しない。
- 既存のスマートフォン専用 `<br>` は目的を確認し、不要なものを削除する。段落や意味の区切りは維持する。
- 文字間隔を広げすぎず、行間と段落間隔で読みやすさを調整する。

`word-break: keep-all`、`overflow-wrap: anywhere`、`white-space` などが日本語本文に広く適用されている場合は、実際の折り返しへの影響を確認してください。特に `keep-all` と `anywhere` の組み合わせを本文全体に使っている場合は、通常の日本語折り返しに戻す方針を基本とします。

ただし、CSS指定だけで原因を断定しないでください。親要素の幅、フォント、`<br>`、表示単位も合わせて確認します。URLや長い英数字は、必要な箇所だけ別に処理します。

### 見出し

- 「明｜確」「理｜由」など、重要な語句の途中で切れる表示を避ける。
- 見出し末尾の1〜2文字だけが次行に残る表示を避ける。
- 幅、文字サイズ、文字間隔、行数を合わせて調整する。
- 意味のある短い語句は、必要に応じて `span` 等でまとめる。
- 見出しの意味単位での改行は許容するが、複数の画面幅で収まることを確認する。
- `text-wrap: balance` は補助として使えるが、日本語の意味を理解して改行する機能ではない。実際の表示で判断する。
- ページ全体、長文全体に `nowrap` や `keep-all` をかけない。

例えば現在の文章に「簡単なお悩みから課題を明確にします。」がある場合は、「簡単なお悩みから」「課題を明確にします。」という意味単位を検討できます。文章は書き換えず、各単位が狭い画面でも収まるように調整してください。

文字サイズの目安は、本文16〜18px、セクション見出し24〜32pxです。Heroは内容に応じて別に判断します。この数値を全箇所に一律適用せず、現在の画面と実際の収まりで決めてください。

## 4. 余白・幅・配置のルール

右側の空白を見つけたら、次の順に原因を追ってください。

1. 外側のコンテナの幅と左右余白。
2. 内側の `width`、`max-width`、左右の `padding`・`margin`。
3. `grid`・`flex` の列、空要素、非表示要素の扱い。
4. PC用の幅・配置指定がスマートフォンにも残っていないか。

特に、画像を非表示にした後も2列構成が残る、本文に割合幅と最大幅を重ねる、親子で左右余白が積み重なる、といった状態を確認してください。

- スマートフォンの外側の左右余白は20〜24px程度を出発点に、サイト内で揃える。
- 内側の部品に同じ余白を重ねて、必要以上に本文を狭めない。
- PC本文の読みやすい行幅、画像との関係、意図的な横スクロールなど、理由のある幅制限は維持する。
- 文章の右端に残る自然な空白を、すべて不具合と判定しない。
- 横はみ出しを隠す目的だけで、ページ全体に `overflow-x: hidden` を追加しない。

「すべて横幅100%」「すべてのmax-widthを削除」のような一括処理はしないでください。問題のある要素に絞って直します。

## 5. 見せ方の判断基準

抽象的な「高級感」「モダン」「AIっぽくない」を理由に、画面を作り替えないでください。内容と現在の問題から配置を判断します。

- 見出しが先に読めて、画像・デモ画面とCTAが見つけやすいこと。
- 補足文が主要情報より目立たないこと。
- 長文まで中央揃えにしないこと。
- 同じ3列カードを、内容の違うセクションへ機械的に展開しないこと。
- 装飾のためだけの番号、アイコン、枠、影を追加しないこと。
- 本文の色を薄くして、スマートフォンで読みにくくしないこと。

カードや中央揃えが現在の内容に適している場合は維持して構いません。今回は既存の配色・画像・ブランド表現を活かします。

## 6. 実装の進め方

1. 修正前のトップページをPC・スマートフォンで記録する。
2. 原因と変更予定を簡潔に示す。
3. 優先順位に沿って必要な箇所を修正する。
4. 実際の画面で確認し、今回の変更による崩れを修正する。
5. 差分を確認し、対象外の変更が入っていないことを確かめる。

既存の共通部品で対応できる場合はそれを使います。ただし、共通化を目的に大量のファイルを変更しないでください。不要な整形や依存関係の更新も行いません。

調査で問題が特定できたら、今回の範囲内の可逆的な修正と検証は続けてください。本番反映、mainへのマージ、リモートへのpushはこの指示の範囲外です。

## 7. 必須の表示確認

- スマートフォン幅：375・390・430px。
- PC幅：1280・1440px。
- 画面幅を基準幅の間でも動かし、切り替え付近の崩れを確認する。
- フォントと画像の読み込みが完了した状態で、ページ下部まで確認する。
- メニュー、CTA、リンクなど、変更に関係する主要操作を確認する。
- 共通CSS・部品を変更した場合は、それを使う代表的な下層ページも確認する。

確認は、次の3つを分けて行ってください。

| 確認項目 | 方法 | 判定すること |
| --- | --- | --- |
| ページ全体の横はみ出し | `scrollWidth` と `clientWidth` を比較し、超過時は原因要素を調べる | 意図しない横スクロールがないか |
| 要素の幅・位置 | 親子の境界、左右余白、列の占有幅を確認する | 不要な幅制限や空き領域がないか |
| 日本語と見た目 | 各幅の画面を目視で確認する | 改行、末尾の孤立、本文の読みやすさ、情報の優先順位 |

`scrollWidth` と `clientWidth` が同じでも、テキスト右側の不自然な空白は検出できません。また座標の一致だけでは、デザインの良し悪しを判定できません。数値確認と画面確認の両方を行ってください。

iPhone Safariの実機確認ができない場合は、エミュレーションや別ブラウザでの確認と区別して報告してください。確認していない環境を「確認済み」にしないでください。

## 8. 完了時の報告

- 問題の原因と修正内容。
- 変更したファイル。
- PC・スマートフォンの修正前後のスクリーンショット。
- 確認した画面幅、ブラウザ、操作、実行したプロジェクト既存のチェック。
- 未確認の環境や、今回の範囲では対応できなかった点。

「レスポンシブ対応済み」「UI・UX改善済み」だけで完了としないでください。何がどう変わったか、画面と差分で確認できる状態にしてください。

この指示だけでデザイン品質が保証されるわけではありません。完成判定は、実際の画面が上記の条件を満たしているかで行ってください。
